# LabTrack — план дальнейшей проработки

**Версия:** 0.1 · **Тип:** ориентир для итераций, не обещание сроков.

## 1. Порядок согласования документации

| Шаг | Артефакт | Результат |
|---|---|---|
| 1 | Vision + PRD + Domain | Подтверждённые роли, ограничения, ключевые сценарии и инварианты |
| 2 | Architecture Overview + ADRs | Границы модулей, транзакционные правила, фоновые задачи, авторизация |
| 3 | Data Model | ERD, таблицы, индексы, ключи, миграции, ограничения целостности |
| 4 | API Specification | OpenAPI, schemas, error contract, pagination, idempotency, authorization |
| 5 | Test Strategy | Unit/integration/E2E, concurrency и security tests, test data |
| 6 | Development & Operations | Docker Compose, конфигурация, CI, логирование, миграции, runbooks |

## 2. Рекомендуемые модули modular monolith

- `identity`: пользователи и auth.
- `organizations`: организации, memberships, roles.
- `samples`: регистрация образцов и машиночитаемые коды.
- `shipments`: комплектация и жизненный цикл партий.
- `receiving`: процесс поэкземплярной приёмки (может остаться подмодулем shipments).
- `audit`: запись и чтение событий.
- `analytics`: агрегаты и метрики.
- `notifications`: best-effort фоновые уведомления.

Не следует заранее создавать отдельные микросервисы, event bus, Kubernetes или сложный DDD-framework.

## 3. Инкременты реализации

**Инкремент A — каркас:** проект, конфигурация, Docker Compose, PostgreSQL, миграции, CI, health checks.

**Инкремент B — доступ:** users, memberships, policy enforcement, авторизационные тесты.

**Инкремент C — отправления:** samples, shipments, items, seal, pickup, event log, транзакционные тесты.

**Инкремент D — приёмка:** receiving, исключения, завершение, API и E2E.

**Инкремент E — эксплуатация и демонстрация:** dashboard, простые уведомления, сиды синтетических данных, README, observability, проверка конкуренции и нагрузки.

## 4. Engineering risks

| Риск | Последствие | Мера |
|---|---|---|
| Утечка данных между учреждениями | Нарушение изоляции | Scope enforcement в сервисном/query слое + negative tests |
| Race condition при seal и изменении items | Неконсистентный манифест | Lock родительской партии в обеих операциях |
| Двойной pickup | Нарушенная цепочка передачи | Lock/CAS + idempotency |
| Изменение приёмки после закрытия | Недостоверная история | Терминальные статусы и append-only события |
| Потеря уведомлений при сбое Celery | Пропущенные сообщения | Retry/backoff, устойчивые записи о заданиях или outbox при строгих требованиях |
| Ложная «точность» отслеживания | Неверная интерпретация интерфейса | Показывать «последнее подтверждённое событие», не GPS |
| Преждевременное хранение PHI | Регуляторные и security-риски | Синтетические данные; отдельный контур проектирования, если изменится scope |

## 5. Решения, которые нужно принять до проектирования БД

1. Нужна ли передача **каждого образца** по QR или достаточно сканировать контейнер при pickup и каждый образец при приёмке?
2. Разрешено ли регистрировать образцы непосредственно в региональном центре, или основная схема строго «отправитель → лаборатория»?
3. Назначает ли курьера отправитель или диспетчер логистики?
4. Нужно ли оформлять инциденты перевозки в P0 или хватит расхождений в результате приёмки?
5. Нужна ли в MVP двухсторонняя передача ответственности, или достаточно подтверждения получающей стороны?

## 6. Definition of Done для MVP

- Полный демонстрационный сценарий выполняется через API и простой интерфейс.
- Все P0 требования покрыты проверяемыми критериями приёмки.
- В БД нельзя создать некорректную повторную привязку образца.
- Есть хотя бы по одному integration test на каждый ключевой переход и negative test на scope violation.
- Есть конкурентные тесты для seal/items и pickup.
- События статусов записываются атомарно с изменением состояния.
- На стенде доступны синтетические данные и инструкция запуска без закрытых внешних сервисов.
- Проведён ручной security review базовых сценариев авторизации и логирования.
