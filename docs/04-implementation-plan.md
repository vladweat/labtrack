## 2. Рекомендуемые модули модульного монолита

- `identity`: пользователи и аутентификация.
- `organizations`: организации, членства, роли.
- `samples`: отдельная регистрация каждой пробирки и машиночитаемые коды.
- `shipments`: партии, маркированные контейнеры, неизменяемый манифест, жизненный цикл.
- `handoffs`: два подтверждения передачи отправитель → курьер и курьер → лаборатория (может остаться подмодулем партии).
- `receiving`: поэкземплярная приёмка пробирок, `MISSING` и `REJECTED` (может остаться подмодулем партии).
- `audit`: запись и чтение событий.
- `analytics`: агрегаты и метрики.
- `notifications`: без гарантии доставки фоновые уведомления.

Не следует заранее создавать отдельные микросервисы, шину событий, Kubernetes или сложный каркас DDD.

## 3. Этапы реализации

**Этап A — каркас:** проект, конфигурация, Docker Compose, PostgreSQL, миграции, CI, проверки работоспособности.

**Этап B — доступ:** пользователи, членства, проверка политик доступа, авторизационные тесты.

**Этап C — регистрация и комплектация:** пробирки, контейнеры, container_items, партии, запечатывание, фиксация манифеста, тесты уникальности и конкурентного наполнения.

**Этап D — передачи и приёмка:** двусторонний забор и доставка, автомат состояний передачи, приёмка каждой пробирки с двумя исключениями, завершение, API и E2E.

**Этап E — эксплуатация и демонстрация:** панель показателей, простые уведомления, начальное заполнение синтетическими данными, README, наблюдаемость, проверка конкуренции и нагрузки.

## 4. Инженерные риски

| Риск | Последствие | Мера |
|---|---|---|
| Утечка данных между учреждениями | Нарушение изоляции | Проверка границ доступа в сервисном слое/слое запросов + негативные тесты |
| Гонка при запечатывании и изменении позиции | Несогласованный манифест | Блокировка родительской партии в обеих операциях |
| Двойной забор или доставка, либо самоподтверждение | Нарушенная цепочка ответственности | Блокировка/CAS + идемпотентность + RBAC + разные идентификаторы исполнителей |
| Контейнер передан, но пробирки автоматически приняты | Неучтённая недостача | Разделить передачу контейнеров и поэкземплярную приёмку |
| Пробирка в двух контейнерах | Неоднозначная прослеживаемость | `UNIQUE(container_items.sample_id)` + транзакционные тесты |
| Изменение приёмки после закрытия | Недостоверная история | Терминальные статусы и события только с добавлением записей |
| Потеря уведомлений при сбое Celery | Пропущенные сообщения | Повторные попытки с увеличением интервала, устойчивые записи о заданиях или таблица исходящих событий при строгих требованиях |
| Ложная «точность» отслеживания | Неверная интерпретация интерфейса | Показывать «последнее подтверждённое событие», не GPS |
| Преждевременное хранение PHI | Регуляторные риски и риски безопасности | Синтетические данные; отдельный контур проектирования, если изменится область доступа |

## 5. Принятые решения и оставшиеся вопросы до БД

**Принятые решения (v0.2):**

1. Каждая пробирка — отдельный `Sample`, включаемый в ровно один `TransportContainer`; партия содержит 1..N контейнеров.
2. Два этапа двусторонней передачи: Отправитель + Курьер при выдаче; Курьер + Оператор лаборатории при доставке. Первое подтверждение не завершает передачу; Курьер может отправить своё подтверждение после синхронизации действий без сети.
3. Только `MISSING` и `REJECTED` являются **категориями** исключений, на SAMPLE и CONTAINER. Контейнерная проблема блокирует доставку, не помечая дочерние пробирки.
4. Для передачи достаточно аутентифицированных действий, без КЭП и юридически значимого документооборота.

**Остаётся уточнить:**

- Курьера назначает отправитель или диспетчер?
- Нужен ли отдельный журнал подтверждений `Handoff` или достаточно структурированной таблицы + общего журнала событий?
- Справочники причин `MISSING`/`REJECTED` и типов материалов.
- Нормативные сроки и правила расчёта опоздания, если они включаются в демонстрацию.

См. [Журнал решений](05-design-decisions.md) и [Доменная модель](03-domain-and-workflows.md).

## 6. Критерии завершения для MVP

- Полный демонстрационный сценарий выполняется через API и простой интерфейс.
- Все P0 требования покрыты проверяемыми критериями приёмки.
- В БД нельзя создать повторную привязку одной пробирки к нескольким контейнерам или партиям.
- Есть хотя бы по одному интеграционному тесту на каждый ключевой переход и негативный тест на нарушение области доступа.
- Есть конкурентные тесты для запечатывания/container_items, двойных подтверждений забора/доставки и поэкземплярной приёмки согласно [тестовой матрице](07-transactions-and-concurrency.md).
- Есть негативные тесты на самоподтверждение и на переход в `IN_TRANSIT`/`RECEIVING` после единственного подтверждения.
- События статусов записываются атомарно с изменением состояния.
- На стенде доступны синтетические данные и инструкция запуска без закрытых внешних сервисов.
- Проведён ручная проверка безопасности базовых сценариев авторизации и логирования.

2. Подготовить архитектурное описание модулей и авторизации; выбрать одну границу сессии БД/транзакции на сценарий использования.

4. Создать первую миграцию Alembic со всеми FK/UNIQUE/CHECK, протестировать миграции на PostgreSQL.
5. Реализовать CRUD только в пределах доменных команд и покрыть матрицу негативных/конкурентных сценариев.
