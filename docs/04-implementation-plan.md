## 2. Рекомендуемые модули modular monolith

- `identity`: пользователи и auth.
- `organizations`: организации, memberships, roles.
- `samples`: отдельная регистрация каждой пробирки и машиночитаемые коды.
- `shipments`: партии, маркированные контейнеры, неизменяемый манифест, жизненный цикл.
- `handoffs`: два подтверждения передачи отправитель → курьер и курьер → лаборатория (может остаться подмодулем shipments).
- `receiving`: поэкземплярная приёмка пробирок, `MISSING` и `REJECTED` (может остаться подмодулем shipments).
- `audit`: запись и чтение событий.
- `analytics`: агрегаты и метрики.
- `notifications`: best-effort фоновые уведомления.

Не следует заранее создавать отдельные микросервисы, event bus, Kubernetes или сложный DDD-framework.

## 3. Инкременты реализации

**Инкремент A — каркас:** проект, конфигурация, Docker Compose, PostgreSQL, миграции, CI, health checks.

**Инкремент B — доступ:** users, memberships, policy enforcement, авторизационные тесты.

**Инкремент C — регистрация и комплектация:** samples, containers, container_items, shipments, seal, фиксация манифеста, тесты уникальности и конкурентного наполнения.

**Инкремент D — передачи и приёмка:** двусторонний pickup и delivery, handoff state machine, приёмка каждой пробирки с двумя исключениями, завершение, API и E2E.

**Инкремент E — эксплуатация и демонстрация:** dashboard, простые уведомления, сиды синтетических данных, README, observability, проверка конкуренции и нагрузки.

## 4. Engineering risks

| Риск | Последствие | Мера |
|---|---|---|
| Утечка данных между учреждениями | Нарушение изоляции | Scope enforcement в сервисном/query слое + negative tests |
| Race condition при seal и изменении items | Неконсистентный манифест | Lock родительской партии в обеих операциях |
| Двойной pickup или delivery, либо самоподтверждение | Нарушенная цепочка ответственности | Lock/CAS + idempotency + RBAC + разные actor IDs |
| Контейнер передан, но пробирки автоматически приняты | Неучтённая недостача | Разделить handoff контейнеров и поэкземплярную приёмку |
| Пробирка в двух контейнерах | Неоднозначная прослеживаемость | `UNIQUE(container_items.sample_id)` + transaction tests |
| Изменение приёмки после закрытия | Недостоверная история | Терминальные статусы и append-only события |
| Потеря уведомлений при сбое Celery | Пропущенные сообщения | Retry/backoff, устойчивые записи о заданиях или outbox при строгих требованиях |
| Ложная «точность» отслеживания | Неверная интерпретация интерфейса | Показывать «последнее подтверждённое событие», не GPS |
| Преждевременное хранение PHI | Регуляторные и security-риски | Синтетические данные; отдельный контур проектирования, если изменится scope |

## 5. Принятые решения и оставшиеся вопросы до БД

**Принятые решения (v0.2):**

1. Каждая пробирка — отдельный `Sample`, включаемый в ровно один `TransportContainer`; партия содержит 1..N контейнеров.
2. Два этапа двусторонней передачи: Sender + Courier при выдаче; Courier + Lab Operator при доставке. Первое подтверждение не завершает передачу; Courier может отправить своё подтверждение после offline sync.
3. Только `MISSING` и `REJECTED` являются **категориями** исключений, на SAMPLE и CONTAINER. Контейнерная проблема блокирует доставку, не помечая дочерние пробирки.
4. Для handoff достаточно аутентифицированных действий, без КЭП и юридически значимого документооборота.

**Остаётся уточнить:**

- Курьера назначает отправитель или диспетчер?
- Нужен ли отдельный журнал подтверждений `Handoff` или достаточно структурированной таблицы + общего журнала событий?
- Справочники причин `MISSING`/`REJECTED` и типов материалов.
- Нормативные сроки и правила расчёта опоздания, если они включаются в демонстрацию.

См. [Decision Log](05-design-decisions.md) и [Domain Model](03-domain-and-workflows.md).

## 6. Definition of Done для MVP

- Полный демонстрационный сценарий выполняется через API и простой интерфейс.
- Все P0 требования покрыты проверяемыми критериями приёмки.
- В БД нельзя создать повторную привязку одной пробирки к нескольким контейнерам или партиям.
- Есть хотя бы по одному integration test на каждый ключевой переход и negative test на scope violation.
- Есть конкурентные тесты для seal/container_items, двойных подтверждений pickup/delivery и поэкземплярной приёмки согласно [тестовой матрице](07-transactions-and-concurrency.md).
- Есть негативные тесты на самоподтверждение и на переход в `IN_TRANSIT`/`RECEIVING` после единственного подтверждения.
- События статусов записываются атомарно с изменением состояния.
- На стенде доступны синтетические данные и инструкция запуска без закрытых внешних сервисов.
- Проведён ручной security review базовых сценариев авторизации и логирования.
## 7. Следующие задачи после проектирования v0.3

1. Зафиксировать дефолтную политику назначения Courier, коррекцию приёмки до закрытия, коды причин и формат QR.
2. Подготовить архитектурное описание модулей и авторизации; выбрать один DB session/transaction boundary на use case.
3. Проверить и утвердить [REST API contract](09-api-specification.md) и [OpenAPI draft](../openapi/labtrack-v1.json), затем зафиксировать стабильную v1-схему.
4. Создать первую Alembic revision со всеми FK/UNIQUE/CHECK, протестировать миграции на PostgreSQL.
5. Реализовать CRUD только в пределах доменных команд и покрыть матрицу негативных/конкурентных сценариев.

> Спроектированная схема не означает существования миграций, таблиц или протестированного приложения.
