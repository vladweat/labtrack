# LabTrack v0.6.1 — Реестр решений (уточнение спецификации)

**Статус требований: ОДОБРЕНЫ для синтетического MVP (2026-11-01).** Все 19 ответов об уточнениях и OPEN-01–04 явно одобрены пользователем. Реестр фиксирует продуктовые решения; это не отчёт о статусе реализации. Одобренные требования имеют приоритет над противоречащими допущениями v0.6. Соответствие требованиям реального применения остаётся вне области проекта.

## 1. Одобрено — Цепочка ответственности (P0)

| ID | Выбор | Принятое правило |
|---|---|---|
| Q01 | A | После подтверждённого получения недоступный назначенный курьер **не заменяется задним числом**. Для затронутых непредъявленных контейнеров используется MISSING, затем региональное предложение и одобрение руководителем лаборатории RETRY/CLOSE_UNDELIVERED. Передачи ответственности заместителю внутри продукта нет |
| Q02 | A | Отправитель может отозвать ожидающее получение курьером. Когда курьера нельзя заменить после фиксации, отправку можно отменить **по существующим правилам отмены** без другой перевозки |
| Q03 | B | Физически предъявленный контейнер без доступного подтверждения курьера может использовать **исключительную приёмку, засвидетельствованную двумя независимыми свидетелями**, с аудитом; её нельзя выдавать за подписанную курьером передачу |
| Q04 | A | Проблема, выявленная после RECEIVED контейнера, никогда не переписывает подтверждённую передачу или ответственность лаборатории; каждый затронутый образец отдельно становится REJECTED с допустимым reason_code и аудитом |
| Q05 | A | Автор предложения REGIONAL_OPERATIONS может отозвать собственное предложение решения ContainerIssue PENDING с причиной и аудитом; LAB_MANAGER может одобрить/отклонить; максимум одно предложение PENDING на проблему |
| Q06 | B | При длительно зависшей передаче региональный оператор открывает инцидент/рассмотрение; LAB_MANAGER назначения или отправитель исходной организации подтверждает соответствующую сторону; нельзя подделывать подтверждение отсутствующего участника |

**Следствие Q02 для безопасности (предложено):** обычный отзыв/отмена допустимы только если физической выдачи не было; при спорной ответственности следует использовать инцидент/рассмотрение, а не подразумевать, что образцы никогда не покидали отправителя.

## 2. Одобрено — Автономная работа, конфликты, идемпотентность (P0)

| ID | Выбор | Принятое правило |
|---|---|---|
| Q07 | B | Использовать время/версию снимка манифеста, выданного сервером; время устройства только справочное; сомнительные/старые действия направляются на ручное рассмотрение, без автоматического подтверждения |
| Q08 | A | Хранить полные ответы воспроизведения автономных команд **90 дней**, затем компактные исторические записи запрета повторного применения выполненных команд предотвращают повторную передачу ответственности; обычные HTTP-ключи идемпотентности могут иметь отдельный TTL |
| Q09 | A | **Любое значимое изменение** состояния отправки до синхронизации вызывает REJECTED и ручное разрешение; автоматическое перебазирование запрещено |
| Q10 | A | Два и более устройств могут иметь независимые очереди курьера, UUID client_command_id, серверные блокировки и проверки устаревания; автоматического объединения очередей нет |
| Q11 | A | После рассмотрения автономной команды старше 24 часов **не применять исходное устаревшее содержимое задним числом**: новая аутентифицированная операция с подключением, если состояние допускает; иначе инцидент |

Время снимка, выданного сервером, **не является криминалистическим доказательством времени физического действия**. Сервер не может наблюдать команды при полной автономности.

## 5. Сохранено из v0.6

- Один пилотный регион, одна центральная лаборатория, только синтетические данные; образец в зафиксированном контейнере отправки; физический манифест неизменен после фиксации (сервис и триггеры PostgreSQL).
- **Обычное** получение: отправитель и назначенный курьер, вся отправка. **Обычная** доставка: курьер и лаборатория, по контейнерам; частичная приёмка разрешена для независимо RECEIVED контейнеров.
- MISSING и REJECTED остаются единственными *типами логистических расхождений*. CustodyIncident — административное дело, а не третий вид расхождения.
- REGIONAL_OPERATIONS предлагает решение, другой LAB_MANAGER назначения одобряет; отклонённые или отозванные предложения не меняют ответственность за контейнер.
- Повторное открытие руководителем с причиной и только добавляемыми версиями. У элементов недоставленного контейнера результаты NULL; смешанное завершение и окончательное закрытие следуют v0.6.
- Redis/Celery никогда не являются авторитетным источником физической ответственности.

## 6. Итоговые одобрения — OPEN-01–04 **ЗАКРЫТЫ / ОДОБРЕНЫ**

Пользователь явно одобрил все четыре рекомендации 2026-11-01. Дополнительного продуктового голосования для синтетического MVP не требуется.

| Решение | Окончательное одобренное правило |
|---|---|
| OPEN-01 | Исключительная приёмка контейнера требует **двух разных физически присутствующих, аутентифицированных сотрудников лаборатории назначения**, включая **хотя бы одного активного LAB_MANAGER**. Каждый подтверждает лично под собственной учётной записью; пользователь с несколькими ролями всё равно учитывается один раз. |
| OPEN-02 | **Нет исключительного RECEIVED без подтверждённого получения всей отправки курьером.** Если получение ожидается, оспаривается или не подтверждено, сначала разрешить его собственный CustodyIncident. Разрешение инцидента не создаёт вымышленного подтверждения курьера; продолжать только если исходное получение действительно подтверждено обычным авторизованным процессом. |
| OPEN-03 | **Региональные операторы начинают рассмотрение.** SENDER_OPERATOR сообщает факты стороны отправления; LAB_MANAGER назначения подтверждает факты лабораторной стороны. Отдельное **административное решение по инциденту** записывает исход, а не цифровую подпись отсутствующего участника. См. детерминированную матрицу ролей/исходов в [Исключениях ответственности](21-custody-exceptions-v061.md). |
| OPEN-04 | Устаревшая команда курьера отклоняется при изменении **manifest_revision, версии целевого контейнера/передачи, подтверждённого получения/этапа ответственности или текущей авторизации участника**. Несвязанные изменения в других частях отправки (например, классификация пробирки другого контейнера) *не считаются автоматически* значимыми и не должны вызывать конфликт, когда все зависимости команды неизменны. Незаметное перебазирование значимого изменения запрещено. |

### Одобренные правила реализации, выведенные из OPEN-03

Для административного решения OPEN-03 REGIONAL_OPERATIONS региона отправки записывает **отдельное разрешение инцидента** после обязательных свидетельств непосредственных участников; его административное действие **не** становится подтверждением передачи курьером или отправителем.

- **Рассмотрение отправления/получения:** активный оператор отправителя исходной организации свидетельствует о фактах своей стороны. Если подтверждено, что физической выдачи *не было*, отправитель может использовать обычный процесс отзыва получения/отмены. Региональное закрытие инцидента само не помечает получение CONFIRMED. Если местонахождение оспаривается, записать нерешённый/эскалированный исход и сохранить состояние передачи.
- **Рассмотрение назначения/доставки:** LAB_MANAGER назначения свидетельствует о фактах лабораторной стороны. Для исключительной приёмки обязательны свидетельства двух сотрудников лаборатории назначения по OPEN-01 (один LAB_MANAGER) и подтверждённое получение курьером; отдельно аудируемое решение регионального оператора может проверить их и пометить контейнер RECEIVED **с доказательством EXCEPTIONAL**, а не поддельной обычной передачей. При отсутствии доказательств оставить доставку неподтверждённой и записать нерешённый исход либо использовать существующий путь ContainerIssue.
- **Независимость:** проверяющий решение не может свидетельствовать за отсутствующего участника; региональный проверяющий не может быть одним из двух свидетелей лаборатории. Авторизация проверяется при решении, аудит фиксирует проверявшего доказательства.

Эти механизмы определяют реализацию одобренного разделения ролей; они не являются юридическим удостоверением ответственности.

### Неблокирующая внешняя проверка (OPEN-05)

Реальное медицинское регулирование, формальные доказательства ответственности, хранение/конфиденциальность и клиническое соответствие требуют одобрения экспертов **до реального развёртывания**. Для MVP только с синтетическими данными это не требуется.

**Критерий спецификации:** OPEN-01–04 разрешены; исключительные и автономные процессы теперь **одобрены к реализации** (при обычной проверке кода, тестах с настоящим PostgreSQL, обеспечении авторизации, тестах аудита и безопасности). Блокирующих продуктовых одобрений для MVP больше нет.
