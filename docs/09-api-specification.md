## 1. Принципы контракта

- JSON UTF-8, `Content-Type: application/json`; идентификаторы `UUID`, метки (`code`) — отдельные непрозрачные строки.
- Время в ответах — RFC 3339 / ISO 8601 с UTC: `2026-11-01T08:00:00Z`. Запросы на `expected_delivery_at` допускают смещение часового пояса, нормализуются в UTC.
- Все бизнес-маршруты требуют `Authorization: Bearer <access_token>`, кроме `POST /auth/login` и `/health/*`.
- Исполнитель и организационные роли извлекаются из проверенного на стороне сервера контекста; клиент не передаёт `actor_id` в командах записи.
- Обязателен `X-Request-ID`? **Нет**: сервер генерирует UUID, если заголовок отсутствует, возвращает `X-Request-ID` и фиксирует его в аудите. Клиентский заголовок должен проходить валидацию UUID, иначе сервер назначает собственный.
- Все списки: `limit` (по умолчанию 20, 1..100), `offset` (по умолчанию 0, максимум 10000); сортировка `created_at DESC, id DESC`, ответ `{items,total,limit,offset}`. Для крупного потока в эксплуатации следует перейти на постраничную выдачу с курсором.
- Поля, отсутствующие в JSON-запросе, не изменяют существующее состояние. Непредусмотренные поля отвергаются (`extra="forbid"`). Строковые причины: удаление краевых пробелов, длина 1..500; пустая/состоящая лишь из пробелов причина не допускается.
- Ни один публичный ответ или QR не содержит сведения о пациенте. Не пересылать в API персональные данные, диагнозы или результаты исследований.
- Успешные маршруты записи синхронно фиксируют транзакцию до ответа; фоновые уведомления не влияют на получаемый статус.
- Непустые входные массивы меток контейнеров при передаче должны точно совпадать по множеству с запечатанным манифестом; дубликаты запрещены.

## 2. Аутентификация и права доступа

### Аутентификация

| Метод | Путь | Запрос | Ответ |
|---|---|---|---|
| `POST` | `/auth/login` | `{email,password}` | `200 {access_token,token_type:"bearer",expires_in:900}` |
| `GET` | `/auth/me` | — | `200 ActorView` |

**Предложение для MVP:** короткоживущий токен доступа 15 минут, повторный вход после истечения, обновление токенов/SSO вне MVP. Для `login` единое сообщение об ошибке логина; ограничение частоты, хэширование и активность учётной записи проверяет модуль идентификации. Точный механизм аутентификации и TTL будут конфигурационными параметрами и нуждаются в реализации/тестировании.

**RBAC + область доступа к ресурсам:** Отправитель — свои исходящие; Курьер — назначенные ему в рамках активного членства в регионе; Лаборатория — входящие своей лаборатории; Администратор организации — только членство своей организации; Региональный аналитик — только агрегаты своего региона. В случае отсутствия области доступа ответ `404` (скрыть существование объекта); для заведомо доступного объекта, но запрещённой команды — `403`.

### Маршруты членства и справочников

| Метод | Путь | Кто | Ответ |
|---|---|---|---|
| `GET` | `/organizations` | Аутентифицированный пользователь в своей области доступа | `200 Paged<Organization>`, фильтры `region_id` и `kind` |
| `GET` | `/organizations/{org_id}/memberships` | Администратор организации этой организации | `200 Paged<Membership>` |
| `POST` | `/organizations/{org_id}/memberships` | Администратор организации | `201 Membership`, тело `{user_id,role}` |
| `PATCH` | `/organizations/{org_id}/memberships/{membership_id}` | Администратор организации | `200 Membership`, тело `{is_active:boolean}` |
| `GET` | `/couriers?region_id=...` | Оператор отправителя региона | `200 Paged<CourierOption>` — активные назначаемые курьеры |

Создание региона и организаций выполняется через CLI начальной настройки/начальное заполнение; публичного API администрирования для этого в P0 нет. Создание первичного пользователя/приглашение сотрудника вне P0; `POST memberships` требует существующего пользователя (начальная настройка). В MVP `role` членство неизменяем: менять роль через деактивацию существующего членства + создание нового.

## 3. Пробирки: каждая пробирка — отдельная сущность

| Метод | Путь | Кто | Ответ |
|---|---|---|---|
| `POST` | `/samples` | Отправитель своей организации | `201 Sample` |
| `GET` | `/samples` | Отправитель своей области доступа (Лаборатория — только по доступным партиям, через манифест) | `200 Paged<Sample>` |
| `GET` | `/samples/{sample_id}` | Отправитель исходной организации, назначенный Курьер или адресная Лаборатория в контексте доступной партии | `200 Sample` (в своей области доступа) |

**CreateSampleRequest:**
~~~json
{
  "origin_organization_id": "11111111-1111-4111-8111-111111111111",
  "material_type": "BLOOD",
  "collected_at": "2026-11-01T08:00:00Z"
}
~~~

- `material_type`: рабочий справочник `BLOOD | URINE | OTHER`; этот выбор **не** несёт клинических нормативов.
- `collected_at` необязательное/допускает null, нет данных пациента.
- Ответ `201 Sample`: `id,code,origin_organization_id,material_type,collected_at,created_at`. Код генерирует сервер (непрозрачный, случайный, не UUID пациента).
- `POST /samples` требует идемпотентности, чтобы повтор при сетевом сбое не создал новую пробирку.

## 4. Партии и контейнерный манифест

| Метод | Путь | Кто | Запрос / Ответ |
|---|---|---|---|
| `POST` | `/shipments` | Отправитель | `201 Shipment`, тело `CreateShipmentRequest` |
| `GET` | `/shipments` | Отправитель/курьер/лаборатория (в своей области доступа) | `200 Paged<Shipment>`; фильтры `status,sender_org_id,destination_org_id` применяются **после** проверки области доступа |
| `GET` | `/shipments/{shipment_id}` | Участник в своей области доступа | `200 Shipment` |
| `GET` | `/shipments/{shipment_id}/manifest` | Участник в своей области доступа | `200 ShipmentManifest` — контейнеры и пробирки с текущими результатами |
| `PATCH` | `/shipments/{shipment_id}/courier` | Отправитель | `200 Shipment`, тело `{courier_user_id:UUID}`, только `DRAFT` |
| `POST` | `/shipments/{shipment_id}/containers` | Отправитель | `201 TransportContainer`, только `DRAFT`; запрос `{}` |
| `DELETE` | `/shipments/{shipment_id}/containers/{container_id}` | Отправитель | `204`, только `DRAFT` и контейнер пуст |
| `POST` | `/shipments/{shipment_id}/containers/{container_id}/items` | Отправитель | `201 ContainerItem`, тело `{sample_id:UUID}` |
| `DELETE` | `/shipments/{shipment_id}/containers/{container_id}/items/{item_id}` | Отправитель | `204`, только `DRAFT` |
| `POST` | `/shipments/{shipment_id}/seal` | Отправитель | `200 Shipment`, тело `{}` |
| `POST` | `/shipments/{shipment_id}/cancel` | Отправитель | `200 Shipment`, тело `{reason:string}` |

**CreateShipmentRequest:**
~~~json
{
  "sender_org_id": "11111111-1111-4111-8111-111111111111",
  "destination_org_id": "22222222-2222-4222-8222-222222222222",
  "expected_delivery_at": "2026-11-01T12:00:00Z"
}
~~~

`region_id` определяется сервером из организаций; отправитель и получатель должны быть активны, иметь один регион и быть разными. Лаборатория назначения обязана иметь `kind=LABORATORY`. `code`, `status=DRAFT`, `version=1` генерирует сервер. Курьер назначается отдельной командой до запечатывания.

**Создание контейнера:** сервер назначает `id` и `code`. В ответе `TransportContainer {id,code,shipment_id,created_at}`. Можно создать пустой контейнер в `DRAFT`, но `seal` потребует каждый контейнер непустым. Удалить непустой контейнер — `409 CONTAINER_NOT_EMPTY`, сначала удалить его позиции.

**Создание позиции:** `ContainerItem {id,container_id,sample_id,receipt_result:null,receipt_reason_code:null,receipt_comment:null}`. Пробирка из другой организации → `404` (не раскрывать), уже добавленная в любой контейнер/партию → `409 SAMPLE_ALREADY_ASSIGNED`. При любой конкурентной операции защита на `UNIQUE(container_items.sample_id)`.

**ShipmentManifest:** список `containers: [{id,code,items:[{id,sample_id,sample_code,material_type,receipt_result,receipt_reason}]}]` плюс `shipment_id,status,sealed_at`; для подтверждений передачи клиент отправляет **только массив кодов контейнеров**, но не статусы пробирок.

**Запечатывание:** проверяет ≥1 контейнер, каждый с ≥1 пробиркой, наличие активного курьера и соответствие организаций; переводит `DRAFT → READY_FOR_PICKUP`, фиксирует `sealed_at`. С этого момента нельзя менять распределение/состав контейнеров. `version` увеличивается на успешную мутацию агрегата.

## 5. Передачи: два подтверждения на каждом этапе

Все четыре команды подтверждения принимают **HandoffConfirmRequest**:
~~~json
{
  "container_codes": ["LT-C-EXAMPLE-01", "LT-C-EXAMPLE-02"]
}
~~~

Пример кодов иллюстративный: в реализации сервер выдаёт криптографически случайные непрозрачные значения. Список должен совпадать с фактическими кодами всех контейнеров запечатанного манифеста, без дубликатов. Нельзя отправлять подмножество.

| Метод | Путь | Роль | Переход состояния | Ответ |
|---|---|---|---|---|
| `POST` | `/shipments/{id}/handoffs/pickup/confirm-release` | Отправитель | `READY_FOR_PICKUP → PICKUP_PENDING` | `200 HandoffActionResult` |
| `POST` | `/shipments/{id}/handoffs/pickup/confirm-pickup` | Назначенный Курьер | `PICKUP_PENDING → IN_TRANSIT` | `200 HandoffActionResult` |
| `POST` | `/shipments/{id}/handoffs/delivery/confirm-delivery` | Назначенный Курьер | `IN_TRANSIT → DELIVERY_PENDING` | `200 HandoffActionResult` |
| `POST` | `/shipments/{id}/handoffs/delivery/confirm-receipt` | Оператор лаборатории назначения | `DELIVERY_PENDING → RECEIVING` | `200 HandoffActionResult` |
| `POST` | `/shipments/{id}/handoffs/pickup/withdraw` | Первоначальный исполнитель отправителя | `PICKUP_PENDING → READY_FOR_PICKUP` | `200 HandoffActionResult` |
| `POST` | `/shipments/{id}/handoffs/delivery/withdraw` | Первоначальный исполнитель курьера | `DELIVERY_PENDING → IN_TRANSIT` | `200 HandoffActionResult` |

**WithdrawRequest:** `{reason:string}`; причина обязательна для операционной прозрачности. Отзыв забора является явным утверждением отправителя, что физической передачи не было и контейнеры остаются на стороне отправителя; утверждение вместе с причиной пишется в аудит. Если факт передачи спорный, применяется разбор инцидента, а не обычный отзыв. Отзыв до второго подтверждения переводит `handoff` в `WITHDRAWN`; следующая попытка создаёт новый `attempt_no`. Нет нового типа инцидента.

**HandoffActionResult:**
~~~json
{
  "shipment_id": "33333333-3333-4333-8333-333333333333",
  "shipment_status": "PICKUP_PENDING",
  "version": 5,
  "handoff": {
    "id": "44444444-4444-4444-8444-444444444444",
    "kind": "PICKUP",
    "attempt_no": 1,
    "status": "PENDING",
    "initiated_by": "55555555-5555-4555-8555-555555555555",
    "initiated_at": "2026-11-01T09:00:00Z",
    "confirmed_by": null,
    "confirmed_at": null
  }
}
~~~

**Ограничения:**
- Одна сторона **не может подтверждать действие за вторую**. `confirmed_by != initiated_by` вне зависимости от набора ролей.
- Активный Курьер обязан совпадать с `shipments.courier_user_id` и иметь допустимую роль в регионе партии.
- Оператор лаборатории обязан действовать от имени `destination_org_id` и иметь соответствующую роль.
- Сверка контейнеров не означает принятие пробирок. Когда партия получает `RECEIVING`, `container_items.receipt_result` ещё NULL.
- При отсутствии контейнера **не подтверждаем передачу** и не имитируем частичную успешную передачу. Отказ в приёмке отдельной пробирки оформляется позже, на стадии приёмки.
- Исполнителя и время определяет сервер по контексту аутентификации и часам БД. Действия, изменение статуса и аудит выполняются в одной транзакции PostgreSQL.

## 6. Приёмка: индивидуальный результат пробирки

| Метод | Путь | Кто | Запрос / Ответ |
|---|---|---|---|
| `PATCH` | `/shipments/{id}/receiving/items/{item_id}` | Оператор лаборатории назначения | `200 ContainerItem`, тело `ReceiptResultRequest`, только `RECEIVING` |
| `POST` | `/shipments/{id}/receiving/complete` | Оператор лаборатории назначения | `200 Shipment`, тело `{}`, только `RECEIVING` |

**ReceiptResultRequest:**
~~~json
{
  "result": "MISSING",
  "reason_code": "SAMPLE_NOT_FOUND", "comment": "Не обнаружена при сверке содержимого контейнера"
}
~~~

Правила:
- `result=ACCEPTED` → `reason_code` и `comment` должны быть null либо отсутствовать.
- `result=MISSING` → пробирка не обнаружена; обязателен валидный `reason_code` с `scope=SAMPLE,kind=MISSING`, комментарий необязателен.
- `result=REJECTED` → пробирка предъявлена, но лаборатория отказала; обязателен `reason_code` с `scope=SAMPLE,kind=REJECTED`.
- Причина берётся из справочника кодов причин по области/категории. Свободный комментарий необязателен, до 500 символов. Не добавлять самостоятельные категории повреждений/температурных инцидентов.
- Нельзя принимать позицию из другой партии, вне своей области доступа или до двух подтверждений доставки.
- **Утверждено v0.5:** до `complete` исправление разрешено с версией результата приёмки и аудитом. После завершения прямое исправление запрещено; LAB_MANAGER может повторно открыть приёмку с причиной и новым сеансом приёмки.
- `complete` читает **все** контейнеры партии и все `container_items` внутри транзакции с блокировкой на партию. Если есть `receipt_result IS NULL` → `409 RECEIVING_INCOMPLETE`. Все `ACCEPTED` → `COMPLETED`; иначе `COMPLETED_WITH_ISSUES`.
- При `REJECTED` лаборатория не обязана в P0 отслеживать дальнейшую физическую судьбу пробирки: возвраты и перераспределение за рамками продукта.

## 7. Аудит и региональная аналитика

| Метод | Путь | Роль | Ответ |
|---|---|---|---|
| `GET` | `/shipments/{id}/events` | Участник в своей области доступа | `200 Paged<AuditEvent>` по `occurred_at ASC,id ASC` |
| `GET` | `/analytics/shipments/summary` | Отправитель, Лаборатория, Администратор организации, Региональный аналитик | `200 ShipmentSummary`; фильтры `region_id,organization_id,from,to` с принудительной проверкой области доступа |

**AuditEvent**: `id,shipment_id,entity_type,entity_id,event_type,actor_id,occurred_at,request_id,details`. События выдачи и получения не объединяются: `RELEASE_CONFIRMED`, `PICKUP_CONFIRMED`, `DELIVERY_CONFIRMED`, `LAB_RECEIPT_CONFIRMED`. В запросе истории на небольших данных сортировка по возрастанию времени.

**ShipmentSummary**: `region_id,from,to,total,by_status:{status:count},completed_with_issues,missing_samples,rejected_samples,overdue_active`. Показатели вычисляются по фактическим записям; нет утверждений о готовой производительности/точности. Региональный аналитик не может запросить данные других регионов.

## 8. Баркоды, поиск и границы безопасности

`POST /scan/resolve` (аутентифицированный POST только для чтения; **без** Idempotency-Key):
~~~json
{"code":"LT-C-EXAMPLE-01"}
~~~

Ответ `200`: `{kind:"CONTAINER",id,shipment_id}` или `{kind:"SAMPLE",id,shipment_id:null|UUID}` с учётом области доступа. Для неизвестного/недоступного кода — одинаковый `404 RESOURCE_NOT_FOUND` без раскрытия данных. Этот маршрут API **не меняет состояние**: ни забор, ни приёмка не происходят от простого сканирования QR.

QR-метка содержит лишь код, не URL с токеном, не ссылку на пациента и не медицинскую информацию. Отображение метки и печать — задача интерфейса/клиента, а генерацию непрозрачного кода обеспечивает серверная часть.

## 9. Idempotency-Key и конкурентный доступ

`Idempotency-Key` — обязательный заголовок (UUID либо 8..128 видимых символов ASCII, конфигурация клиента) для:
- `POST /samples`, `POST /shipments`, `POST /shipments/{id}/containers`, `POST .../items`;
- `PATCH .../courier`, `POST .../seal`, `POST .../cancel`;
- всех `POST .../handoffs/*`, `PATCH .../receiving/items/*` и `POST .../receiving/complete`.

Для создания/изменения членства также требуется ключ. Для `DELETE` допускается повторный запрос без ключа идемпотентности: повтор после удаления может вернуть `404`, состояние не восстанавливается.

**Порядок обработки:**
1. Аутентифицировать исполнителя, проверить данные запроса, определить операцию = метод + канонический маршрут + конкретные идентификаторы ресурсов.
2. В транзакции зарезервировать `(actor_id,operation,key)`, сопоставить хэш канонического запроса; при повторе вернуть сохранённый статус/тело ответа.
3. Для новой команды выполнить организационные проверки политик и `SELECT ... FOR UPDATE` Shipment (если команда изменяет агрегат партии). Записать изменения + аудит + идемпотентный ответ в **той же** транзакции.
4. После фиксации транзакции вернуть зафиксированный ответ. Любая ошибка в транзакции откатывает изменение, аудит и идемпотентную запись.

Транзакция не включает отправку Celery, сетевые запросы или ожидание внешних API. TTL сохранённого ответа для MVP предлагается 24 часа; очистка идемпотентных ключей не изменяет события аудита. Параллельный запрос с **другим ключом** может получить `409 INVALID_STATE` или `409 VERSION_CONFLICT`.

Пример:
~~~http
POST /api/v1/shipments/33333333-3333-4333-8333-333333333333/handoffs/pickup/confirm-pickup
Authorization: Bearer <token>
Idempotency-Key: 8e04d4bd-c687-4f34-8532-5c98e4903431
Content-Type: application/json

{"container_codes":["LT-C-EXAMPLE-01","LT-C-EXAMPLE-02"]}
~~~

## 10. Стандартный контракт ошибок

Все ошибки (кроме штатной платформенной 422 до преобразования) приводятся обработчиками исключений API к единой JSON форме:

~~~json
{
  "error": {
    "code": "INVALID_STATE",
    "message": "Shipment cannot be confirmed in its current state",
    "details": {"current_status": "DRAFT", "required_status": "PICKUP_PENDING"},
    "request_id": "66666666-6666-4666-8666-666666666666"
  }
}
~~~

| HTTP | Код ошибки | Когда |
|---|---|---|
| 400 | `INVALID_REQUEST` | Нарушена семантика запроса за пределами проверки схемы |
| 401 | `UNAUTHORIZED` | Отсутствует/просрочен/невалиден токен |
| 403 | `FORBIDDEN` | Ресурс доступен, операция запрещена ролью |
| 404 | `RESOURCE_NOT_FOUND` | Не найдено либо скрыто по политике |
| 409 | `INVALID_STATE` | Команда не разрешена текущим статусом |
| 409 | `SAMPLE_ALREADY_ASSIGNED` | Пробирка уже в контейнере |
| 409 | `CONTAINER_NOT_EMPTY` | Попытка удалить непустой контейнер |
| 409 | `MANIFEST_MISMATCH` | Сканированный набор контейнеров не совпадает с манифестом |
| 409 | `RECEIVING_INCOMPLETE` | Не все пробирки обработаны |
| 409 | `SELF_CONFIRMATION_FORBIDDEN` | Одно лицо пытается завершить обе стороны передачи |
| 409 | `IDEMPOTENCY_KEY_REUSED` | Один ключ и отличающиеся данные запроса |
| 409 | `VERSION_CONFLICT` | Конкурентное изменение состояния/версии |
| 422 | `VALIDATION_ERROR` | Проверка Pydantic (включая недостающую/пустую причину) |
| 429 | `RATE_LIMITED` | Превышен лимит аутентификации/запросов (после реализации) |
| 503 | `SERVICE_UNAVAILABLE` | Временная недоступность PostgreSQL или обязательной зависимости |

`details` должны быть безопасны: не включать чужие данные при недостаточной области доступа, не возвращать SQL/стек вызовов/password_hash. Ошибка 500 — общий, не раскрывающий внутренности текст с `request_id`.

## 12. Сквозные примеры и приёмочные проверки

**Успешный сценарий:** 10 отдельных пробирок → Shipment → 2 контейнера → 10 позиций → назначение курьера → запечатывание → подтверждение выдачи отправителем → подтверждение забора курьером → подтверждение доставки курьером → подтверждение получения лабораторией → по каждой пробирке `PATCH receiving/items` → завершение. Для 8 `ACCEPTED`, 1 `MISSING`, 1 `REJECTED` итог `COMPLETED_WITH_ISSUES`, две причины и четыре независимых подтверждения видны в журнале.

**Критические тесты API:**
- До ответа курьера статус не может стать `IN_TRANSIT`; до ответа лаборатории не может стать `RECEIVING`.
- После передачи лаборатория видит все `receipt_result=null`; сканирование контейнера не проставляет `ACCEPTED`.
- Попытка подтвердить одновременно чужим курьером, тем же исполнителем, при несовпадении кодов или в другом регионе отклоняется.
- Конкурентные добавления одной пробирки в разные контейнеры дают один успех, один `409`.
- `seal` одновременно с изменением состава не оставляет полуманифеста.
- Повтор с `Idempotency-Key` после сетевого тайм-аута не создаёт второе событие аудита.
- Завершение приёмки с необработанной пробиркой даёт `409`; после завершения изменение возможно только через повторное открытие LAB_MANAGER с версиями изменений.
- Региональный аналитик не получает строки Sample/ContainerItem по прямым ID.
