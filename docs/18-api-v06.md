## 1. Изменённые конечные точки (относительно v0.5)

**Старые конечные точки доставки всей отправки исключены из проекта v0.6**:
- `POST /shipments/{id}/handoffs/delivery/confirm-delivery`
- `POST /shipments/{id}/handoffs/delivery/confirm-receipt`
- `POST /shipments/{id}/handoffs/delivery/withdraw`
- `POST /shipments/{id}/container-issues/resolve` (единоличное немедленное разрешение)

**Заменяющие конечные точки:**

| Метод | Путь относительно /api/v1 | Роль / значение |
|---|---|---|
| POST | `/shipments/{id}/containers/{container_id}/handoffs/delivery/confirm-delivery` | Назначенный курьер инициирует доставку **одного контейнера** |
| POST | `/shipments/{id}/containers/{container_id}/handoffs/delivery/confirm-receipt` | LAB_OPERATOR или LAB_MANAGER назначения подтверждает тот же контейнер |
| POST | `/shipments/{id}/containers/{container_id}/handoffs/delivery/withdraw` | Курьер-инициатор отзывает ожидающую попытку с указанием причины |
| GET | `/shipments/{id}/containers/{container_id}/handoffs` | История этого контейнера только для чтения в пределах доступа |
| POST | `/shipments/{id}/container-issues/{issue_id}/proposals` | REGIONAL_OPERATIONS предлагает RETRY_DELIVERY/CLOSE_UNDELIVERED; **ответственность не меняется** |
| GET | `/shipments/{id}/container-issues/{issue_id}/proposals` | Уполномоченные операторы/руководители видят полную историю предложений |
| POST | `/shipments/{id}/container-issues/{issue_id}/proposals/{proposal_id}/decide` | LAB_MANAGER назначения выполняет APPROVE/REJECT; одобренное предложение вызывает атомарный переход контейнера/проблемы |
| GET | `/shipments/{id}/receiving/history` | Включает сеанс частичной приёмки и версии |
| POST | `/shipments/{id}/receiving/reopen` | LAB_MANAGER назначения может повторно открыть завершённый сеанс; второй руководитель не нужен |
| POST | `/courier/sync` | Очередь автономных команд курьера, отдельная транзакция для каждой команды |
| GET | `/operations/stalled-shipments` | Зависшие действия, видимые серверу, в пределах региона; отдельно от невидимой локальной очереди |

Сохранено:
- Получение всей отправки `/shipments/{id}/handoffs/pickup/confirm-release` и `.../confirm-pickup` остаётся двусторонним.
- `POST /shipments/{id}/container-issues` создаёт MISSING/REJECTED **для одного контейнера**, не блокируя остальные.
- `PATCH /shipments/{id}/receiving/items/{item_id}` разрешён, когда контейнер элемента RECEIVED и есть сеанс OPEN, в том числе при общем статусе отправки PARTIALLY_DELIVERED.
- `POST /shipments/{id}/receiving/complete` должен проверять **окончательный исход всех контейнеров** и явные результаты пробирок только в контейнерах RECEIVED.

Все операции записи требуют `Idempotency-Key`, кроме `POST /courier/sync`, где у каждой команды неизменный `client_command_id`.

## 2. Доставка отдельного контейнера

Инициирование:

```http
POST /api/v1/shipments/{shipment_id}/containers/{container_id}/handoffs/delivery/confirm-delivery
Authorization: Bearer <token>
Idempotency-Key: ...
Content-Type: application/json

{"container_code":"LT-C-EXAMPLE-02"}
```

Сервер проверяет назначение курьера, действующее членство курьера, наличие контейнера в зафиксированном манифесте и состояние IN_TRANSIT, совпадение кода, отсутствие уже подтверждённой доставки. Транзакция: создать передачу DELIVERY PENDING с `container_id`; контейнер DELIVERY_PENDING; вычислить Shipment.status и аудит. Ответ `HandoffActionResult` включает `container_id` и `container_status`.

Подтвердить получение с тем же `{"container_code":"..."}` на соответствующей конечной точке контейнера. Сотрудник лаборатории принадлежит организации назначения, его `user_id` отличается от инициатора-курьера. Транзакция: пометить передачу CONFIRMED, контейнер RECEIVED, задать received_at/by, открыть receiving_session при первом получении, вычислить статус отправки и аудит. **Массового принятия** результатов дочерних пробирок нет.

Отзыв `{"reason":"..."}` доступен только курьеру-инициатору при PENDING; контейнер становится IN_TRANSIT. Инцидент BLOCKED также отзывает ожидающую попытку доставки в той же транзакции. Подтверждённые записи неизменны.

## 3. Проблема контейнера и решение двумя сторонами

Сообщение `POST /shipments/{id}/container-issues`:

```json
{"container_id":"44444444-4444-4444-8444-444444444444","kind":"REJECTED","reason_code":"CONTAINER_SEAL_UNACCEPTABLE","comment":"Описание отказа"}
```

Только сотрудник лаборатории назначения может сообщить REJECTED для контейнера, тогда как курьер/лаборатория могут сообщить MISSING. Этот контейнер переходит в BLOCKED, остальные не меняются. Контейнер RECEIVED нельзя задним числом пометить REJECTED через эту конечную точку.

Предложение:

```http
POST /api/v1/shipments/{id}/container-issues/{issue_id}/proposals
Authorization: Bearer <token>
Idempotency-Key: ...
Content-Type: application/json

{"action":"CLOSE_UNDELIVERED","reason":"Контейнер не поступил и передача не может быть завершена"}
```

Ответ 201 `ContainerIssueResolutionProposal(status=PENDING)`; **контейнер остаётся BLOCKED**.

Решение (другой LAB_MANAGER лаборатории назначения):

```http
POST /api/v1/shipments/{id}/container-issues/{issue_id}/proposals/{proposal_id}/decide
Authorization: Bearer <token>
Idempotency-Key: ...
Content-Type: application/json

{"decision":"APPROVE","reason":null}
```

Либо `{"decision":"REJECT","reason":"Требуется уточнение обстоятельств"}`. При одобрении в **одной транзакции PostgreSQL** предложение становится APPROVED; проблема RESOLVED/CLOSED_UNDELIVERED; контейнер IN_TRANSIT/UNDELIVERED_CLOSED; вычисляемый Shipment.status обновляется; добавляется аудит. При отклонении предложение становится REJECTED, проблема остаётся OPEN, контейнер BLOCKED. Затем разрешено новое предложение. `409` для устаревших решений и дублирующихся ожидающих предложений. Автоматического одобрения нет, даже если пользователь имеет обе роли; `proposed_by != decided_by`.

## 4. Приёмка и завершение

Запрос результата образца (категории прежние, структурированный код причины):

```json
{"result":"MISSING","reason_code":"SAMPLE_NOT_FOUND","comment":null}
```

Элемент доступен для записи **только когда именно его контейнер RECEIVED**, с двусторонней передачей доставки CONFIRMED и сеансом приёмки OPEN. Контейнер BLOCKED или UNDELIVERED_CLOSED не может иметь результаты пробирок. Один оператор лаборатории может записывать результаты контейнеров RECEIVED, пока другой контейнер ещё не доставлен.

Завершение возвращает `409 UNRESOLVED_CONTAINERS`, если хотя бы один контейнер остаётся PREPARED/IN_TRANSIT/DELIVERY_PENDING/BLOCKED. Возвращает `409 RECEIVING_INCOMPLETE`, если у пробирки внутри контейнера RECEIVED нет явного результата. При наличии контейнеров UNDELIVERED_CLOSED их пробирки сохраняют нулевой результат; отправка завершается как `COMPLETED_WITH_ISSUES`. Если все контейнеры окончательно недоставлены, отправка автоматически переходит в CLOSED_UNDELIVERED при последнем одобрении, без завершения приёмки пробирок.

Повторное открытие руководителем лаборатории из завершённого статуса создаёт новый сеанс OPEN с причиной; никогда не открывает повторно контейнер UNDELIVERED_CLOSED или отправку CLOSED_UNDELIVERED.

## 5. Автономная работа курьера — изменённый формат действий

Пакет `POST /courier/sync` остаётся атомарным независимо для каждой команды; стабильный `client_command_id` служит ключом идемпотентности в одном пространстве имён участника `courier_offline_command`. Хранить `client_performed_at` (утверждение устройства) отдельно от `recorded_at` (авторитетное время сервера).

Два типа команд (OpenAPI `oneOf`):

**Получение отправки курьером**, требует полный набор кодов зафиксированных контейнеров:

```json
{
  "client_command_id":"11111111-1111-4111-8111-111111111111",
  "shipment_id":"22222222-2222-4222-8222-222222222222",
  "action":"COURIER_CONFIRM_PICKUP",
  "container_codes":["C-001","C-002","C-003"],
  "expected_manifest_version":4,
  "client_performed_at":"2026-11-01T10:00:00Z"
}
```

**Инициирование доставки одного контейнера**, требует ровно один ID/код контейнера:

```json
{
  "client_command_id":"33333333-3333-4333-8333-333333333333",
  "shipment_id":"22222222-2222-4222-8222-222222222222",
  "container_id":"44444444-4444-4444-8444-444444444444",
  "container_code":"C-002",
  "action":"COURIER_INITIATE_CONTAINER_DELIVERY",
  "expected_manifest_version":4,
  "client_performed_at":"2026-11-01T10:45:00Z"
}
```

`expected_manifest_version` сравнивается со стабильным зафиксированным Shipment.manifest_revision, **а не** изменяемым Shipment.version. Устаревшее состояние или отсутствие текущих ролей → `REJECTED` с ошибкой, без незаметного применения. Возраст очереди более 24 часов → `REVIEW_REQUIRED`, без изменения ответственности до ручного рассмотрения. Невидимое серверу действие очереди не может создавать серверные напоминания; локально показывать прошедшее время, а панель отдельно обнаруживает зависшие серверные передачи. Лаборатория не может подтвердить несинхронизированную доставку курьера.

`CourierSyncResult.outcome`: `APPLIED`, `ALREADY_APPLIED`, `REJECTED`, `REVIEW_REQUIRED`, `RETRYABLE`; результат включает `container_id`, где применимо, `client_performed_at` и `recorded_at`, код ошибки. HTTP 200 уровня пакета допускает ошибки отдельных команд. Тайм-аут после фиксации → повтор точного ID возвращает ALREADY_APPLIED с теми же авторитетными отметками времени.

**Правила ручного рассмотрения:** демонстрация v0.6 не одобряет незаметно автономное действие старше 24 часов. Безопасное поведение по умолчанию — отклонить выполнение и потребовать новую передачу с действующей аутентификацией и подключением после расследования либо использовать существующий путь проблемы контейнера/предложения при спорной физической ответственности. Введение способа задним числом одобрять задержанные утверждения устройства требует отдельных правил и **не** подразумевается API синхронизации.

## 6. Контракты аналитики и уведомлений

`GET /analytics/shipments/summary` возвращает агрегированные региональные итоги и показатели; расширить:
- Интервалы временного ряда (ежедневно/еженедельно, необязательный параметр запроса и определение границ UTC).
- Агрегированный разрез по учреждениям (организация отправления и лаборатория назначения; по-прежнему одна центральная лаборатория).
- Средняя длительность доставки от **серверного времени подтверждённого получения отправки курьером** до **серверного времени последней подтверждённой доставки контейнера**, исключая UNDELIVERED_CLOSED; для частично доставленных отправок отдельно возвращать `average_received_container_delivery_seconds`.
- Счётчики `container_missing`, `container_rejected`, `sample_missing`, `sample_rejected`, `partial_delivery_shipments`, `closed_undelivered`.
- Количество ожидающих/спорных случаев и p95 времени в состоянии для операционной панели с точными определениями знаменателей; не смешивать недоставленное со временем успешной доставки.
- REGIONAL_ANALYST с доступом только для чтения видит агрегаты, а не детали элементов или пациентов.

Уведомления только внутри приложения, через панель/журнал событий. Участники зависшего шага видят свой этап; REGIONAL_OPERATIONS получает сведения об эскалации при превышении сроков. Celery может создавать уведомления без гарантии доставки; панель агрегирует PostgreSQL, чтобы пропуски не скрывали зависшие действия.

## 7. Правила ошибок и авторизации

| Код | Условие |
|---|---|
| `INVALID_STATE` | Команда контейнера при недопустимом статусе доставки |
| `CONTAINER_NOT_RECEIVED` | Попытка отметить пробирку контейнера, не подтверждённого лабораторией |
| `UNRESOLVED_CONTAINERS` | Попытка завершения при контейнере без окончательного исхода |
| `RECEIVING_INCOMPLETE` | Отсутствуют результаты в принятых контейнерах |
| `PROPOSAL_ALREADY_PENDING` | Второе активное предложение для той же проблемы |
| `RESOLUTION_APPROVAL_SELF` | Один человек предлагает и одобряет |
| `PROPOSAL_STALE` | Проблема/состояние изменились до решения |
| `OFFLINE_REVIEW_REQUIRED` | Возраст очереди превышает 24 часа, требуется рассмотрение человеком |
| `OFFLINE_COMMAND_STALE` | Состояние сервера изменилось до автономной синхронизации |
| `IDEMPOTENCY_KEY_REUSED` | ID команды повторён с другим телом |
| `MANIFEST_MISMATCH` | Отсканированный или переданный код отличается от зафиксированного манифеста |

Использовать 401/403 для неавторизованных пользователей и маскирующий 404, когда нужно предотвратить IDOR; 409 для бизнес-конфликтов и 422 для несоответствия структуры запроса/кода. Никогда не представлять неподтверждённую доставку контейнера или ожидающую автономную команду как успешную передачу ответственности.
