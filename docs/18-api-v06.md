Current v0.6.1 requirements supersede it where they differ: `/api/v1`, Bearer JWT, and error shape `{error:{code,message,details,request_id}}`. ## 1. Changed endpoints (from v0.5)

**Old Shipment-wide delivery endpoints are withdrawn from the v0.6 draft**:
- `POST /shipments/{id}/handoffs/delivery/confirm-delivery`
- `POST /shipments/{id}/handoffs/delivery/confirm-receipt`
- `POST /shipments/{id}/handoffs/delivery/withdraw`
- `POST /shipments/{id}/container-issues/resolve` (unilateral immediate resolution)

**Replacement endpoints:**

| Method | Path relative to /api/v1 | Role / meaning |
|---|---|---|
| POST | `/shipments/{id}/containers/{container_id}/handoffs/delivery/confirm-delivery` | Assigned Courier initiates **one container** delivery |
| POST | `/shipments/{id}/containers/{container_id}/handoffs/delivery/confirm-receipt` | Destination LAB_OPERATOR or LAB_MANAGER confirms that same container |
| POST | `/shipments/{id}/containers/{container_id}/handoffs/delivery/withdraw` | Original Courier withdraws a pending attempt, with reason |
| GET | `/shipments/{id}/containers/{container_id}/handoffs` | Scoped read-only history for this container |
| POST | `/shipments/{id}/container-issues/{issue_id}/proposals` | REGIONAL_OPERATIONS proposes RETRY_DELIVERY/CLOSE_UNDELIVERED; **no custody mutation** |
| GET | `/shipments/{id}/container-issues/{issue_id}/proposals` | Scoped operators/managers view full proposal history |
| POST | `/shipments/{id}/container-issues/{issue_id}/proposals/{proposal_id}/decide` | Destination LAB_MANAGER APPROVE/REJECT; approved proposal triggers atomic container/issue transition |
| GET | `/shipments/{id}/receiving/history` | Includes partial-receiving session and revisions |
| POST | `/shipments/{id}/receiving/reopen` | Destination LAB_MANAGER can reopen completed session; no second manager |
| POST | `/courier/sync` | Courier offline command queue, each command its own transaction |
| GET | `/operations/stalled-shipments` | Region-scoped server-visible stalled actions; separate from unseen local queue |

Retained:
- Whole-Shipment Pickup `/shipments/{id}/handoffs/pickup/confirm-release` and `.../confirm-pickup` remain bilateral.
- `POST /shipments/{id}/container-issues` creates MISSING/REJECTED **for one container**, without blocking unrelated containers.
- `PATCH /shipments/{id}/receiving/items/{item_id}` permitted when item's container is RECEIVED and an OPEN session exists, including when overall Shipment is PARTIALLY_DELIVERED.
- `POST /shipments/{id}/receiving/complete` must check **all containers dispositioned** plus explicit tube results only in RECEIVED containers.

All writes require `Idempotency-Key` except `POST /courier/sync`, where each command has immutable `client_command_id`.

## 2. Per-container delivery

Initiate:

```http
POST /api/v1/shipments/{shipment_id}/containers/{container_id}/handoffs/delivery/confirm-delivery
Authorization: Bearer <token>
Idempotency-Key: ...
Content-Type: application/json

{"container_code":"LT-C-EXAMPLE-02"}
```

Server checks courier assigned, Courier membership current, container in sealed manifest and IN_TRANSIT, code matches, no confirmed delivery already. Transaction: create PENDING DELIVERY handoff scoped to `container_id`; container DELIVERY_PENDING; derive Shipment.status and audit. Response `HandoffActionResult` includes `container_id` and `container_status`.

Confirm receipt with identical `{"container_code":"..."}` on corresponding per-container endpoint. Lab member destination org, `user_id` differs from Courier initiator. Transaction: mark handoff CONFIRMED, container RECEIVED, set received_at/by, open receiving_session if first received, derive Shipment status and audit. **No bulk acceptance** of child tube results.

Withdraw `{"reason":"..."}` only by original Courier while PENDING; container becomes IN_TRANSIT. A BLOCKED incident also withdraws a pending delivery attempt in the same transaction. Confirmed records immutable.

## 3. Container issue and two-party resolution

Report `POST /shipments/{id}/container-issues`:

```json
{"container_id":"44444444-4444-4444-8444-444444444444","kind":"REJECTED","reason_code":"CONTAINER_SEAL_UNACCEPTABLE","comment":"Описание отказа"}
```

Only a destination Lab member may report container REJECTED, while Courier/Lab can report MISSING. Status transitions this container to BLOCKED, not the others. Container RECEIVED cannot be retrospectively REJECTED via this endpoint.

Proposal:

```http
POST /api/v1/shipments/{id}/container-issues/{issue_id}/proposals
Authorization: Bearer <token>
Idempotency-Key: ...
Content-Type: application/json

{"action":"CLOSE_UNDELIVERED","reason":"Контейнер не поступил и передача не может быть завершена"}
```

Response 201 `ContainerIssueResolutionProposal(status=PENDING)`; **container remains BLOCKED**.

Decision (distinct LAB_MANAGER of destination laboratory):

```http
POST /api/v1/shipments/{id}/container-issues/{issue_id}/proposals/{proposal_id}/decide
Authorization: Bearer <token>
Idempotency-Key: ...
Content-Type: application/json

{"decision":"APPROVE","reason":null}
```

Or `{"decision":"REJECT","reason":"Требуется уточнение обстоятельств"}`. On approval, in **one PostgreSQL transaction** the proposal becomes APPROVED; issue RESOLVED/CLOSED_UNDELIVERED; container becomes IN_TRANSIT/UNDELIVERED_CLOSED; derived Shipment.status updated; append audit. On rejection, proposal becomes REJECTED, issue remains OPEN and container BLOCKED. A new proposal is then allowed. `409` for stale decisions and duplicate pending proposals. No auto-approval even if a user holds both roles; `proposed_by != decided_by`.

## 4. Receiving and completion

Sample result request (unchanged in category, structured reason code):

```json
{"result":"MISSING","reason_code":"SAMPLE_NOT_FOUND","comment":null}
```

An item is writable **only when its specific container is RECEIVED**, with a CONFIRMED two-party Delivery Handoff and OPEN receiving session. A container that is BLOCKED or UNDELIVERED_CLOSED cannot have tube outcomes. A single lab operator may record results from RECEIVED containers while another is not yet delivered.

Completion returns `409 UNRESOLVED_CONTAINERS` if any container remains PREPARED/IN_TRANSIT/DELIVERY_PENDING/BLOCKED. Returns `409 RECEIVING_INCOMPLETE` if a tube inside a RECEIVED container lacks an explicit result. When some containers UNDELIVERED_CLOSED, their tubes retain null outcome; Shipment completes with `COMPLETED_WITH_ISSUES`. If all containers permanently undelivered, Shipment transitions automatically to CLOSED_UNDELIVERED on final approval, without tube receiving completion.

Lab Manager reopening from completed status creates a new OPEN session with reason; never reopens an UNDELIVERED_CLOSED container or Shipment CLOSED_UNDELIVERED.

## 5. Courier offline — changed action format

`POST /courier/sync` batch remains independently atomic per command; stable `client_command_id` is used as idempotency key under one actor-wide namespace `courier_offline_command`. Store `client_performed_at` (device claim) separately from `recorded_at` (server authoritative).

Two types of commands (OpenAPI `oneOf`):

**Shipment pickup**, requires complete set of sealed container codes:

```json
{
  "client_command_id":"11111111-1111-4111-8111-111111111111",
  "shipment_id":"22222222-2222-4222-8222-222222222222",
  "action":"COURIER_CONFIRM_PICKUP",
  "container_codes":["C-001","C-002","C-003"],
  "expected_manifest_version":4,
  "client_performed_at":"2026-11-01T10:00:00Z"
}
```

**Single-container Delivery initiation**, requires exactly one container ID/code:

```json
{
  "client_command_id":"33333333-3333-4333-8333-333333333333",
  "shipment_id":"22222222-2222-4222-8222-222222222222",
  "container_id":"44444444-4444-4444-8444-444444444444",
  "container_code":"C-002",
  "action":"COURIER_INITIATE_CONTAINER_DELIVERY",
  "expected_manifest_version":4,
  "client_performed_at":"2026-11-01T10:45:00Z"
}
```

`expected_manifest_version` compares to the stable frozen Shipment.manifest_revision, **not** mutable Shipment.version. Stale state or missing current roles → `REJECTED` with an error, never silently applied. Queue age over 24 hours → `REVIEW_REQUIRED`, no custody mutation without manual review. A queued action invisible to the server cannot produce server-side reminders; locally show elapsed time and Dashboard separately detects stalled server handoffs. Lab cannot confirm a Courier's unsynced delivery.

`CourierSyncResult.outcome`: `APPLIED`, `ALREADY_APPLIED`, `REJECTED`, `REVIEW_REQUIRED`, `RETRYABLE`; result includes `container_id` where relevant, `client_performed_at` and `recorded_at`, and error code. A batch-level HTTP 200 permits per-command failure. Timeout after commit → exact ID replay returns ALREADY_APPLIED with identical authoritative timestamps.

**Manual review policy:** v0.6 demo does not silently approve an offline action older than 24h. The safe default is reject for execution and require a fresh live authenticated handoff following human investigation, or follow the existing container issue/proposal route when physical custody is disputed. Introducing a route to retroactively approve delayed device claims requires separate policy and is **not** implicit in the sync API.

## 6. Analytics and notification contracts

`GET /analytics/shipments/summary` returns aggregate region totals and rates; extend with:
- Time-series period buckets (daily/weekly optional query parameter and UTC boundary definition).
- Facility-level aggregate breakdown (origin org and destination lab; still one central lab).
- Average delivery duration measured from **confirmed Shipment Pickup server timestamp** to **last confirmed Container Delivery server timestamp**, excluding UNDELIVERED_CLOSED; for partially delivered shipments expose `average_received_container_delivery_seconds` separately.
- `container_missing`, `container_rejected`, `sample_missing`, `sample_rejected`, `partial_delivery_shipments`, `closed_undelivered` counts.
- Pending/disputed counts and p95 time-in-state for operations dashboard, with exact denominator definitions; avoid mixing undelivered with successful delivery latency.
- Read-only REGIONAL_ANALYST sees aggregates, not item- or patient-level details.

In-app notifications only, via dashboard/event log. Participants of the stalled step see their own stage; REGIONAL_OPERATIONS receives escalation metadata when deadlines exceeded. Celery may generate notifications best-effort; Dashboard aggregates from PostgreSQL so misses do not hide stalled actions.

## 7. Error/authorization rules

| Code | Condition |
|---|---|
| `INVALID_STATE` | per-container command in impossible delivery status |
| `CONTAINER_NOT_RECEIVED` | attempt to mark a tube whose container has not been confirmed by lab |
| `UNRESOLVED_CONTAINERS` | attempt to finalize while any container unresolved |
| `RECEIVING_INCOMPLETE` | missing results in received containers |
| `PROPOSAL_ALREADY_PENDING` | second active proposal for same issue |
| `RESOLUTION_APPROVAL_SELF` | same person proposes and approves |
| `PROPOSAL_STALE` | issue/state changed before decision |
| `OFFLINE_REVIEW_REQUIRED` | queue age exceeds 24h and requires human review |
| `OFFLINE_COMMAND_STALE` | server state changed before offline sync |
| `IDEMPOTENCY_KEY_REUSED` | command ID replayed with different body |
| `MANIFEST_MISMATCH` | scanned or submitted code differs from sealed manifest |

Use 401/403 for unauthorized users and masked 404 when necessary to prevent IDOR; 409 for business conflicts and 422 for request shape/code mismatch. Never represent an unconfirmed container delivery or pending offline command as successful custody transfer.
