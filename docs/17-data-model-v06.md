### Новая таблица: container_issue_resolution_proposals

| Столбец | Тип | Назначение |
|---|---|---|
| `id` | UUID PK | Неизменный идентификатор предложения |
| `issue_id` | UUID NOT NULL FK | Одна проблема контейнера |
| `action` | TEXT NOT NULL | `RETRY_DELIVERY` или `CLOSE_UNDELIVERED` |
| `reason` | TEXT NOT NULL (1–500) | Объяснение регионального оператора |
| `status` | TEXT NOT NULL | `PENDING,APPROVED,REJECTED,WITHDRAWN` |
| `proposed_by` | UUID NOT NULL FK | REGIONAL_OPERATIONS |
| `proposed_at` | TIMESTAMPTZ NOT NULL | Серверное время |
| `decided_by` | UUID NULL FK | LAB_MANAGER назначения, другой пользователь |
| `decided_at` | TIMESTAMPTZ NULL | Серверное время |
| `decision_reason` | TEXT NULL | Обязательно для REJECTED; необязательно для APPROVED |

Проверять `proposed_by <> decided_by` при принятии решения и согласованность времени и участника ожидающего/принятого решения. Создать уникальный частичный индекс:

```sql
CREATE UNIQUE INDEX uq_issue_pending_proposal
ON container_issue_resolution_proposals(issue_id)
WHERE status='PENDING';
```

Предложение не изменяет проблему или контейнер. Одобрение в одной транзакции проверяет активную проблему, состояние BLOCKED, совпадение отправки/региона/назначения и действующее членство и атомарно обновляет предложение, проблему, контейнер, агрегатный статус отправки и аудит. Отклонение меняет только предложение и аудит, оставляя проблему OPEN и контейнер BLOCKED. Устаревшие предложения решения получают 409.

## 2. Условная уникальность и целостность передач

Оставить `Handoff.kind` равным PICKUP или DELIVERY. Прежнее `UNIQUE(shipment_id,kind,attempt_no)` **не должно** применяться к DELIVERY после ввода передач по контейнерам; заменить условными уникальными индексами:

```sql
CREATE UNIQUE INDEX uq_pickup_attempt
ON handoffs(shipment_id,attempt_no)
WHERE kind='PICKUP';

CREATE UNIQUE INDEX uq_delivery_attempt
ON handoffs(container_id,attempt_no)
WHERE kind='DELIVERY';

CREATE UNIQUE INDEX uq_pickup_active_or_confirmed
ON handoffs(shipment_id)
WHERE kind='PICKUP' AND status IN ('PENDING','CONFIRMED');

CREATE UNIQUE INDEX uq_delivery_active_or_confirmed
ON handoffs(container_id)
WHERE kind='DELIVERY' AND status IN ('PENDING','CONFIRMED');
```

`CHECK` БД: `(kind='PICKUP' AND container_id IS NULL) OR (kind='DELIVERY' AND container_id IS NOT NULL)`. Обеспечить совпадение `handoffs(shipment_id,container_id)` с `transport_containers(shipment_id,id)` подходящим составным внешним ключом при ненулевом container_id и обязательным внешним ключом отправки. Существующие подтверждённые передачи нельзя отзывать, перезаписывать или удалять.

`transport_containers.received_by` должен совпадать с участником подтверждённой передачи DELIVERY (транзакционный сервис / защищённый инвариант БД), отличным от инициатора. Не принимать автоматически все `container_items`.

## 3. Коды причин и проверка приёмки

Загрузить начальные `issue_reason_codes(scope,kind,code,label,is_active)`, `scope=SAMPLE|CONTAINER`, `kind=MISSING|REJECTED`. Пользователь выбрал **фиксированный начальный каталог**, а не управление CRUD.

- `container_issues.reason_code_id` соответствует `scope=CONTAINER,kind=container_issues.kind`.
- `container_items.receipt_reason_code_id` соответствует `scope=SAMPLE,kind=receipt_result` для MISSING/REJECTED; NULL для ACCEPTED. `receipt_comment` необязателен, не более 500 символов.
- Простого внешнего ключа UUID недостаточно для проверки области и вида. Использовать защищённый триггер или составной внешний ключ с областью/видом вместе с проверкой в приложении.
- `receipt_result=NULL` для UNDELIVERED_CLOSED **обязателен**, это не дефект качества данных; нельзя создавать вымышленные результаты.

## 4. Явные инварианты завершения

Для отправки S обозначим:

`N = total containers` (N ≥ 1 после фиксации), `R = RECEIVED`, `U = UNDELIVERED_CLOSED`.

- `complete_receiving` допустим только если `R >= 1`, `R + U = N`, сеанс приёмки OPEN, у каждого элемента контейнера RECEIVED ненулевой результат, **у каждого элемента контейнеров UNDELIVERED_CLOSED результат NULL**.
- Если `U>0` или хотя бы один принятый элемент MISSING/REJECTED → `COMPLETED_WITH_ISSUES`; иначе `COMPLETED`.
- `R=0, U=N` → `CLOSED_UNDELIVERED`; завершённого сеанса приёмки этой отправки быть не может.
- Незавершённый контейнер означает `R+U < N`; завершение отправки отклоняется, даже если у каждого уже принятого элемента есть результат.
- При повторном открытии руководителем оставить R/U неизменными, открыть новый сеанс, сбросить текущий статус отправки в RECEIVING, сохранить историю предыдущих сеансов, аудита и версий.

Вычислять укрупнённый статус отправки под блокировкой родительской строки по функции приоритетов из [Процессов](16-domain-workflows-v06.md). **Не** пытаться использовать простой `CHECK`, подсчитывающий дочерние записи.

## 5. Порядок блокировок, изоляция и безопасная идемпотентность

Все изменяющие команды (включая одобрения, доставку контейнера, приёмку и синхронизацию автономной работы):

1. Разобрать запрос, выполнить аутентификацию и проверить структуру. Начать транзакцию.
2. Зарезервировать/проверить ключ идемпотентности в глобальной области участник + операция + ключ; для синхронизации использовать стабильное пространство имён `courier_offline_command`.
3. **Сначала блокировать отправку**: `SELECT ... FOR UPDATE`. Перед возвратом сохранённого ответа повторно проверять авторизацию и активное членство.
4. Блокировать необходимые контейнеры / проблему / предложение / передачу / сеанс приёмки и элементы в **детерминированном порядке**, затем проверять состояние и роль. В текущем MVP меняется ровно одна отправка.
5. Записать все зависимые изменения, добавить события/версии, пересчитать укрупнённый статус, увеличить Shipment.version, сохранить результат идемпотентности в **той же транзакции**.
6. Зафиксировать; затем попытаться опубликовать уведомление Celery/Redis без гарантии доставки. Потеря уведомления не отменяет бизнес-событие.

Конкурентная доставка **разных контейнеров одной отправки** сериализуется родительской блокировкой; это намеренно простой и надёжный выбор для регионального пилота.

Если автономной команде больше 24 часов или она устарела, **не применять автоматически**. Возвращать стабильный результат рассмотрения/конфликта; записывать подходящий серверный аудит при поступлении команды на сервер, а не пока она невидима на устройстве. Сервер не может наблюдать ещё не полученную очередь устройства.

## 6. Гарантии триггеров PostgreSQL и оговорка о взаимных блокировках

Пользователь одобрил триггеры БД для защиты зафиксированного манифеста:
- Отклонять INSERT/DELETE/UPDATE связей отправки с контейнерами и идентичности связи контейнера с образцами после фиксации.
- Разрешать изменение атрибутов приёмки только для элементов контейнера RECEIVED, если отправка имеет сеанс приёмки OPEN, через авторизованный путь приложения.
- Сохранять неизменными статус принятого контейнера и подтверждённую передачу; события версий приёмки доступны только для добавления.

**Важно:** триггеры уровня строки при прямом SQL могут получить блокировку дочерней строки **до** блокировки родительской отправки. Поэтому триггер, читающий/блокирующий отправку, необходим для согласованности фиксации, но сам по себе **не доказывает отсутствие взаимных блокировок** с конкурентной транзакцией приложения, блокирующей отправку первой. Ограничивать прямую запись ролями БД, обеспечить протокол «сначала родитель» в приложении и тестировать обнаружение/повтор после взаимных блокировок при неожиданном прямом SQL. Не обещать невозможных гарантий только за счёт порядка триггеров.

## 7. Миграция и индексы

На тот момент репозиторий **не содержал реализованной серверной части или файлов миграций**. Это целевые правила DDL, а не выполненные миграции.

Рекомендуемый порядок миграции:
1. Расширить проверку статуса отправки значением PARTIALLY_DELIVERED, обновить правила бизнес-состояний, добавить container.delivery_status и столбцы received_*.
2. Привязать передачи DELIVERY к контейнерам; заменить прежнюю уникальность; добавить частичные индексы и составной внешний ключ.
3. Ввести container_issue_resolution_proposals; заменить прямое разрешение путём предложения/решения. Сохранить историю проблем.
4. Обновить ограничения приёмки, чтобы принятые контейнеры обрабатывались при отправке PARTIALLY_DELIVERED.
5. Добавить начальные коды причин, триггеры сеансов приёмки, защиту зафиксированного манифеста, заполнить синтетические наборы данных.
6. Индексы: `transport_containers(shipment_id,delivery_status)`, `container_issues(container_id,status)`, `resolution_proposals(issue_id,status)`, `container_items(container_id,receipt_result)`, `handoffs(container_id,kind,status)`, `receipt_revisions(container_item_id,changed_at)`.
7. Добавить интеграционные тесты с **настоящим PostgreSQL**; повторить Alembic upgrade на одноразовой БД.

## 8. Матрица приёмки SQL и интеграции

- Два отдельных контейнера можно принимать параллельными запросами без двойной передачи; операции безопасно сериализуются родительской блокировкой.
- Блокировка C3 не затрагивает C1/C2. Элементы C1/C2 можно отмечать; C3 нельзя.
- Создание предложения PENDING → состояние доставки неизменно; оператор другого региона не может предлагать решение.
- Одобрение LAB_MANAGER требует другого `user_id` и членства в лаборатории назначения; устаревшее/отклонённое предложение одобрить нельзя.
- Гонка двух одобрений одного предложения → один переход, одна запись аудита; повтор с тем же ключом идемпотентности возвращает сохранённый результат.
- Прямые изменения зафиксированного манифеста через SQL завершаются ошибкой. Повторно открытая приёмка никогда не позволяет менять состав контейнеров/образцов.
- Нельзя завершить отправку, пока хоть один контейнер не имеет окончательного исхода. Смесь недоставленных и принятых завершается как COMPLETED_WITH_ISSUES; все недоставленные — как CLOSED_UNDELIVERED.
- Возвращать раздельно заявленное клиентское и авторитетное серверное время, обрабатывать повторы и устаревшую синхронизацию.
