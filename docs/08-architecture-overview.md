## 1. Контекст и цели

LabTrack — внутренний региональный сервис прослеживаемости лабораторных пробирок, объединённых в маркированные транспортные контейнеры и партии. Участники: учреждение-отправитель, назначенный курьер, лаборатория назначения и региональный аналитик.

Основные требования: индивидуальная прослеживаемость пробирки; **двустороннее подтверждение** выдачи и доставки контейнеров; поэкземплярная приёмка; две категории исключений `MISSING` и `REJECTED` на уровне SAMPLE/CONTAINER; блокировка недоставки, повторное открытие руководителем лаборатории, синхронизация действий курьера без сети, аудит, организационная изоляция и согласованность.

Приложение **не** заменяет ЛИС/МИС, не хранит данные реальных пациентов, не выполняет исследования, не определяет клиническую пригодность, не заявляет GPS-отслеживание или юридически значимую электронную подпись. В демонстрации используются только синтетические данные.

## 2. Выбранная архитектура

**Модульный монолит + PostgreSQL как достоверный источник данных.** Один процесс FastAPI для REST API, отдельно Celery обработчик/планировщик для необязательных фоновых задач, Redis как брокер/кэш. Внешние API и AI не обязательны для MVP. Дополнительно у курьера есть PWA с минимальной очередью действий без сети; её команды применяются к PostgreSQL только после защищённой синхронизации.

~~~mermaid
flowchart TB
    UI["Web UI / API clients"] --> N["Nginx / reverse proxy"]
    N --> A["FastAPI application"]
    subgraph M["Modular monolith"]
      A --> ID["identity / access"]
      A --> ORG["organizations"]
      A --> SAMPLE["samples"]
      A --> SHIP["shipments / containers / handoffs / receiving"]
      A --> ANA["analytics"]
      A --> AUD["audit / idempotency"]
    end
    ID --> PG[("PostgreSQL")]
    ORG --> PG
    SAMPLE --> PG
    SHIP --> PG
    ANA --> PG
    AUD --> PG
    A -. "publish after commit, best effort" .-> R[("Redis broker")]
    R --> W["Celery worker"]
    W --> PG
    B["Celery beat"] --> R
~~~

**Почему так:** основная сложность — атомарные изменения одного Shipment, проверка организационного доступа и прослеживаемость. Распределённые транзакции между микросервисами усложнили бы корректность. Отдельный обработчик оправдан уведомлениями и периодическим обнаружением просрочек, но ни Redis, ни Celery не становятся источником истины по состоянию партии.

## 3. Модули и владение данными

| Модуль | Владеет | Основные обязанности | Зависимости |
|---|---|---|---|
| `identity` | `users`, аутентификация, работа с учётными данными | Вход, текущий исполнитель, активный пользователь | PostgreSQL |
| `organizations` | `regions`, `organizations`, членства | Организационные границы доступа, назначение ролей, активное членство | модуль идентификации |
| `samples` | `samples` | Регистрация одной пробирки, уникальные непрозрачные метки, чтение в своей области доступа | организации |
| `shipments` | `shipments`, `transport_containers`, `container_items`, `handoffs` | Редактирование манифеста, запечатывание, две передачи, приёмка, финализация | пробирки, доступ, аудит |
| `audit` | `audit_events` | Журнал только с добавлением записей бизнес-событий и логика доступа для чтения | модуль идентификации |
| `idempotency` | `idempotency_records` | Атомарное резервирование ключа и повтор сохранённого ответа | модуль идентификации |
| `analytics` | агрегации SQL, не дублирующие таблицы | Сводки по региону, организации и статусу | партии, доступ |
| `notifications` | необязательные задачи/уведомления | Уведомления без гарантии доставки, контроль сроков | Celery/Redis/PostgreSQL |

`Shipment` — транзакционный агрегат. `containers`, `handoffs` и `receiving` на MVP остаются частями модуля `shipments`, а не отдельными независимыми микросервисами. Код модуля `analytics` читает данные через слой запросов и не изменяет состояния партий.

Это **пример организации**, не требование создавать четыре слоя в каждом небольшом модуле. Маршрутизатор FastAPI: разбор/проверка → текущий исполнитель → сценарий использования → ответ. Сценарий использования: политика + транзакция + агрегат + аудит. Модели SQLAlchemy не становятся публичными схемами ответа. Нет самостоятельного универсального каркаса репозиториев, локатора сервисов или шины событий.

Предлагаемый стек: Python с аннотациями типов, FastAPI, Pydantic, асинхронный SQLAlchemy 2.x, Alembic, PostgreSQL, Redis, Celery, pytest, Docker Compose и Nginx. Фиксированные версии зависимостей выбираются при начальной настройке проекта; здесь не утверждаются.

## 5. Аутентификация / авторизация / организационные границы доступа

- **Аутентификация:** электронная почта + пароль, защищённый Argon2id (или сопоставимым современным алгоритмом хэширования паролей), Bearer токен доступа с коротким сроком жизни; сервер независимо проверяет активность пользователя. Токены обновления/SSO — P1. В MVP допускается повторный вход по истечении токена доступа.
- **Субъект / исполнитель:** `user_id`, активное членство в организациях (с ролями), региональные роли; брать из проверенной учётной записи/БД, не из произвольных заголовков клиента.
- **Границы доступа субъекта:** Отправитель читает только свои отправления и образцы; Лаборатория — только адресованные лаборатории; Курьер — только назначенные партии; LAB_MANAGER повторно открывает приёмку в своей лаборатории; REGIONAL_OPERATIONS вручную разрешает блокировки в своём регионе; Администратор организации управляет членством своей организации; Региональный аналитик получает только региональные агрегаты.
- **RBAC + проверки принадлежности** в запросах/сценариях использования. Случайные UUID и QR-коды **не** являются средствами авторизации.
- Для курьера в пилоте допустима активная роль `COURIER` в логистической организации **того же региона**, что и партия; назначение подтверждает Отправитель, пока не добавлен диспетчер. При чтении курьер фильтруется по `courier_user_id` и членству в регионе.
- Поставщик удостоверений, сброс пароля, многофакторная аутентификация и юридически значимые подписи не входят в MVP. Для эксплуатации с реальными медицинскими данными потребуется самостоятельное проектирование безопасности и соблюдения нормативных требований.

**Негативные тесты безопасности:** IDOR на чужие Sample/Shipment/Контейнер/Handoff, самоподтверждение двух сторон пользователем с несколькими ролями, деактивированный Курьер, назначение между регионами, доступ регионального аналитика к поэкземплярным данным.

## 6. Транзакции, конкурентный доступ и согласованность

**Базовая стратегия:** один PostgreSQL `AsyncSession`/транзакция на сценарий записи, `READ COMMITTED`, `SELECT ... FOR UPDATE` на родительском `shipments`. Все операции изменения дочерних контейнеров, позиций, передач и приёмки сначала блокируют строку партии. Согласованный порядок блокировок защищает от взаимных блокировок.

- `seal` фиксирует манифест 1..N контейнеров, каждый содержит ≥1 пробирку; состав и распределение **неизменяемы** после запечатывания.
- `confirm_release` → `PICKUP_PENDING`; только подтверждение **другого** назначенного курьера → `IN_TRANSIT`.
- `confirm_delivery` → `DELIVERY_PENDING`; только подтверждение **другого** оператора лаборатории в лаборатории назначения → `RECEIVING`.
- Подтверждение передачи контейнера **никогда** не помечает его пробирки как `ACCEPTED`.
- В `RECEIVING` каждая `container_item` получает `ACCEPTED`, `MISSING` или `REJECTED`. Финализация проверяет отсутствие NULL; отклонения требуют причину.
- Каждое изменение статуса, попытка передачи, результат пробирки и событие аудита сохраняются **атомарно**; при ошибке аудита — откат транзакции всей команды.
- `UNIQUE(container_items.sample_id)` предотвращает двойную привязку пробирки даже между разными Shipment (которые блокируются независимо).

**Идемпотентность:** для критичных команд записи хранить `(actor_id,operation,key,request_hash,response)` в PostgreSQL в одной транзакции с изменениями и аудитом. Повтор с теми же данными запроса возвращает сохранённый ответ, с другим → `409 IDEMPOTENCY_KEY_REUSED`. Примерный TTL 24 часа (предлагаемая настройка, не продемонстрированная гарантия). После фиксации транзакции уведомления в P0 без гарантии доставки; потеря публикации возможна и должна быть явно обозначена.

**Решение v0.5:** обязательны и сервисные ограничения, и триггеры PostgreSQL, блокирующие изменения идентичности/состава запечатанного манифеста даже прямым SQL. Изменение результатов при повторно открытом сеансе приёмки разрешено с версиями изменений только с добавлением записей. Пока это **план реализации**, не работающая гарантия.

Подробный порядок и тесты: [Транзакции и конкурентный доступ](07-transactions-and-concurrency.md).

## 7. Наблюдаемость и операции

- Структурированные журналы JSON с `request_id` и безопасными идентификаторами; не логировать токены доступа, пароли, пациентов, запросы с секретами.
- `/health/live` не требует БД; `/health/ready` проверяет соединение с PostgreSQL. Отказ Redis не должен превращать успешно выполненную бизнес-команду в ошибку, если задача уведомления без гарантии доставки.
- Метрики для будущих графиков: пропускная способность команд, доля `409`, длительность транзакций, p95 ожидания блокировки, число ожидающих передач, доля партий с `MISSING`/`REJECTED`, количество просроченных партий, фоновые повторные попытки.
- Задачи Celery обязаны быть идемпотентны; бизнес-события читаются из PostgreSQL. Уведомление не меняет статус. Периодические сканирования учитывают неизменное `expected_delivery_at`.
- Alembic миграции на запуске окружения применяются отдельной командой, **не** конкурентно каждым обработчиком.
- Docker Compose для разработки, проверки работоспособности, контейнеры без root, конфигурация через переменные окружения/секреты, HTTPS на обратном прокси в эксплуатации, резервное копирование PostgreSQL и тесты восстановления — до фактической эксплуатации.
- Защита API: список разрешённых источников CORS, ограничение частоты аутентификации, ограничения размера запроса, тайм-ауты, фиксация версий зависимостей и поиск секретов. Эти меры являются списком будущих работ, а не уже реализованными мерами защиты.

## 8. Тестовая пирамида и порядок реализации

1. **Модульные тесты:** переходы `Shipment`, инварианты, RBAC, формирование манифеста и сверка множества контейнеров.
2. **Интеграционные тесты на реальном PostgreSQL:** FK/UNIQUE/CHECK, применение/откат миграций на тестовой базе, запрет IDOR, атомарность состояния/аудита/идемпотентности.
3. **Конкурентный доступ:** два курьера, два изменения одной позиции, `seal` одновременно с редактированием, уникальность пробирки в разных партиях, два одновременных `complete_receiving`.
4. **E2E:** 10 пробирок → два контейнера → четыре подтверждения двух передач → 8 ACCEPTED, 1 MISSING, 1 REJECTED → COMPLETED_WITH_ISSUES; чтение региональной сводки.

Реализацию начинаем с каркаса/конфигурации/миграций, затем реализуем аутентификацию/доступ, пробирки/контейнеры, передачи, приёмку, панель показателей. Не вводим микросервисы или AI до успешного сквозного MVP.

## 9. Утверждённые решения и оставшиеся операционные допущения

В следующих документах эти пункты являются **рабочими допущениями**, а не заменой принятых DEC-001–003:

- **Утверждено:** Оператор отправителя назначает активного курьера своего региона **только пока Shipment DRAFT**; диспетчер не нужен.
- **Утверждено:** в `RECEIVING` Оператор лаборатории может исправить неверную отметку с receipt_revision и аудитом. LAB_MANAGER вправе повторно открыть завершённую приёмку с новой сессией и причиной.
- **Утверждено:** `MISSING`/`REJECTED` требуют кода причины из справочника, комментарий необязателен. Обе категории применяются к SAMPLE и CONTAINER.
- **Утверждено:** QR содержит только непрозрачный код без PHI; подтверждения сверяют полный манифест. Для курьера без сети фиксируется `manifest_revision`, независимая от `Shipment.version`.
- В MVP только синхронные сценарии записи REST и без гарантии доставки фоновые уведомления, без транзакционной таблицы исходящих событий.

**Открыто для операционного утверждения:** физическая ответственность за отклонённый контейнер, длительность ручной проверки команд без сети, конкретные коды причин и юридический смысл временных меток действий без сети.

См. [v0.5 Доменная модель](10-domain-hardening-v05.md), [Синхронизация курьера](11-offline-sync-protocol.md), [Изменения БД](12-data-model-v05.md), [Изменения API](13-api-v05.md).

## 10. Изменения модулей и инфраструктуры v0.5

- `shipments`: ContainerIssue, DELIVERY_BLOCKED/CLOSED_UNDELIVERED, ручное разрешение, сеансы приёмки и версии её результатов; всё под блокировкой Shipment.
- `organizations`: отдельные роли LAB_MANAGER и REGIONAL_OPERATIONS без глобального обхода проверок.
- `samples`: синтетические непрозрачные внешние ссылки ЛИС (1:N).
- `courier_offline`: PWA IndexedDB + API синхронизации, без токенов в локальной очереди; синхронизация использует те же сценарии использования, что сетевые команды.
- `notifications`: Celery без гарантии доставки; Панель показателей обнаруживает зависшие операции независимо от Redis.
- `database`: триггеры PostgreSQL для запечатанного манифеста, индексы кодов причин/проблем/сеансов, тесты прямого SQL доступа и конкуренции.
