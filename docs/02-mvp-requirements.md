# LabTrack — Требования к MVP (PRD/SRS)

> **Исторический документ (до v0.6).** Здесь могут встречаться устаревшие правила передачи всей партии, одностороннего разрешения контейнерных проблем и устаревшие пути API. Актуальные и приоритетные требования: [Решения v0.6](15-decisions-v06.md), [Доменная модель v0.6](16-domain-workflows-v06.md), [Модель данных v0.6](17-data-model-v06.md), [API v0.6](18-api-v06.md). Не использовать этот документ в одиночку как нормативный контракт.

**Версия:** 0.5 (обновлённая спецификация P0)
**Приоритет:** `P0` — обязателен для первого демо; `P1` — после стабильного MVP.
**Язык требований:** формулировка «система должна» означает проверяемое поведение.

## 1. Бизнес-процесс

1. Оператор отправителя регистрирует **каждую пробирку отдельно** как `Sample` с индивидуальной меткой.
2. Создаёт `Shipment`, добавляет в него один или несколько `TransportContainer` с собственными метками, распределяет пробирки между ними.
3. Назначает курьера и фиксирует неизменяемый манифест пробирок и контейнеров через `seal`.
4. **Передача отправитель → курьер**: Отправитель подтверждает выдачу (`PICKUP_PENDING`), назначенный Курьер подтверждает получение (`IN_TRANSIT`).
5. **Передача курьер → лаборатория**: Курьер подтверждает доставку (`DELIVERY_PENDING`), Оператор лаборатории подтверждает получение контейнеров (`RECEIVING`).
6. При проблеме с предъявлением контейнера Курьер/лаборатория фиксирует `MISSING` или `REJECTED` для контейнера; вся доставка блокируется без частичной передачи.
7. При обычной доставке Оператор лаборатории проверяет пробирки **по одной**: `ACCEPTED`, `MISSING` или `REJECTED`; для исключения нужен код причины.
8. После явной обработки каждой пробирки партия закрывается как `COMPLETED` или `COMPLETED_WITH_ISSUES`; Руководитель лаборатории может повторно открыть приёмку с аудитом.
9. Курьер может подготовить действия без сети; сервер применяет их только после защищённой синхронизации.

**Важно:** передача контейнера подтверждается двумя пользователями, но подтверждение контейнера само по себе **не** означает приёмку всех пробирок.

## 2. Функциональные требования P0

| Идентификатор | Требование | Критерий приёмки |
|---|---|---|
| FR-001 | Пользователь должен аутентифицироваться | Неавторизованные запросы к защищённым маршрутам отклоняются |
| FR-002 | Все операции должны проверять роль и организационную область доступа | Нельзя прочесть/изменить чужую партию подбором идентификатора |
| FR-003 | Администратор организации управляет членством и ролями своих сотрудников | Операции за пределами своей организации отклоняются |
| FR-004 | Оператор отправителя регистрирует образец с уникальным непредсказуемым кодом | Совпадения кодов исключены ограничением БД, код не включает сведения о пациенте |
| FR-005 | Оператор отправителя создаёт черновик партии с одной организацией-отправителем и одной лабораторией назначения | Разные организации/лаборатории в одной партии недопустимы |
| FR-006 | Контейнеры и их пробирки можно добавлять, удалять и перемещать только в `DRAFT` | После запечатывания манифест неизменяем |
| FR-007 | Одна пробирка не может находиться в двух контейнерах или партиях | `UNIQUE(container_items.sample_id)` защищает и при конкурентных запросах |
| FR-008 | `seal` фиксирует манифест контейнеров и пробирок | В партии ≥1 непустой контейнер, курьер назначен; после запечатывания манифест неизменяем |
| FR-009 | Выдача курьеру требует двух подтверждений | Только после подтверждений отправителя и назначенного курьера партия переходит из `PICKUP_PENDING` в `IN_TRANSIT` |
| FR-010 | Получение контейнеров лабораторией требует двух подтверждений | Курьер → `DELIVERY_PENDING`, Оператор лаборатории адресной лаборатории → `RECEIVING` |
| FR-011 | Оператор лаборатории фиксирует результат каждой пробирки | `ACCEPTED`, `MISSING`, `REJECTED`; для исключения обязателен код причины из справочника, комментарий опционален |
| FR-012 | Приёмка завершается только после явной отметки каждой позиции | Неотмеченные позиции препятствуют завершению |
| FR-013 | Итоговый статус партии различает доставку без/с расхождениями | `COMPLETED` — все `ACCEPTED`; иначе `COMPLETED_WITH_ISSUES` |
| FR-014 | Все значимые действия фиксируются в журнале аудита/событий | Для действия видны время, исполнитель, объект, тип, причина и request_id |
| FR-015 | Операционная панель показателей показывает количества по статусам, просрочки и расхождения | Числа согласуются с транзакционными данными |
| FR-016 | Партия отменяется до начала двустороннего подтверждения выдачи | `CANCELLED` только из `DRAFT`/`READY_FOR_PICKUP`, с причиной |
| FR-017 | Повторная доставка команды не должна создавать повторную передачу или дублирующую партию | Поддерживается `Idempotency-Key` для критичных команд и/или безопасная повторная попытка по версии |
| FR-018 | Метки образца и контейнера содержат только случайные идентификаторы | Сканирование без авторизации не раскрывает внутренние сведения |

| FR-019 | Партия содержит 1..N маркированных контейнеров | В каждом контейнере ≥1 пробирка при запечатывании; контейнер принадлежит ровно одной партии |
| FR-020 | Передачи требуют двух разных уполномоченных пользователей | Отправитель и назначенный курьер, затем тот же Курьер + Оператор лаборатории; самоподтверждение запрещено |
| FR-021 | Первый участник может отозвать ожидающую передачу до второго подтверждения | `withdraw_release`/`withdraw_delivery` журналируются и возвращают прежнее состояние |
| FR-022 | Сканирование контейнера не подтверждает автоматически все пробирки | Каждая пробирка должна быть отдельно отмечена на приёмке |
| FR-023 | В P0 допустимы только две категории исключений | `MISSING` / `REJECTED` для `SAMPLE` или `CONTAINER`; для каждой нужен reason_code |

| FR-024 | Контейнер MISSING/REJECTED блокирует всю доставку | IN_TRANSIT/DELIVERY_PENDING → DELIVERY_BLOCKED; Результаты приёмки пробирок не меняются |
| FR-025 | REGIONAL_OPERATIONS разрешает блокировку | RETRY_DELIVERY → IN_TRANSIT; CLOSE_UNDELIVERED → CLOSED_UNDELIVERED с аудитом |
| FR-026 | LAB_MANAGER может повторно открыть завершённую приёмку | Новый сеанс приёмки, обязательная причина, сохранение прежних версий изменений |
| FR-027 | Результаты приёмки версионируются | Каждое исправление сохраняет receipt_revision и AuditEvent |
| FR-028 | Причины двух исключений структурированы | Код причины соответствует области объекта и категории; комментарий необязателен |
| FR-029 | Запечатанный манифест защищён триггерами PostgreSQL | Прямые SQL-изменения состава после запечатывания отклоняются |
| FR-030 | Курьер может работать без сети | Локальная очередь до синхронизации не меняет сервер; повторная попытка на стороне сервера идемпотентна |
| FR-031 | В пилоте одна центральная лаборатория | Получатель проверяется по региональной настройке |
| FR-032 | Синтетические непрозрачные ссылки на внешнюю ЛИС | Не раскрывают пациентские данные, допускают несколько ссылок на Sample |
| FR-033 | Зависшие передачи доступны REGIONAL_OPERATIONS | Ручная обработка; Celery без гарантии доставки не влияет на источник данных |

### Допущения MVP

- Каждая пробирка — отдельный `Sample`; пробирки объединяются в `TransportContainer`; партия содержит 1..N контейнеров. Повторные перевозки остаются за рамками.
- Два подтверждения — аутентифицированные действия пользователей, **не** юридически значимая электронная подпись. Подтверждение передачи контейнера не означает результатов приёмки его содержимого.
- Частичные **успешные** передачи контейнеров, возвраты и новые типы инцидентов вне MVP. Отказ **от контейнера** поддерживается: это `REJECTED` с блокировкой всей доставки.
- `expected_delivery_at` может задаваться при подготовке партии как операционный плановый срок, но не означает клинической пригодности.
- События фиксируются по факту действия пользователя; GPS-местоположение не вычисляется.
- В MVP приемка возможна с несколькими последовательными сканированиями в одной сессии `RECEIVING`; финализация — отдельное действие.

## 4. Уведомления и фоновые задания

- `P0`: асинхронная обработка внутренних событий (например, уведомление о готовности/прибытии и о завершении с проблемами); сбой уведомления не отменяет основной переход.
- `P0`: периодический пересчёт/выявление опозданий относительно `expected_delivery_at` для незавершённых партий.
- `P0`: события бизнес-переходов фиксируются транзакционно, вместе с изменением состояния. Отправка сообщения во внешнюю систему не должна выполняться до коммита БД.
- `P1`: Email/Telegram/SMS, расширенные отчёты, интеграционные события и гарантированная доставка сообщений через транзакционную таблицу исходящих событий (если появятся критичные интеграции).

## 5. Нефункциональные требования

| Идентификатор | Требование / решение |
|---|---|
| NFR-001 | PostgreSQL обеспечивает ссылочную целостность, уникальность и необходимые транзакционные блокировки |
| NFR-002 | Конкурирующие команды не должны обходить допустимые переходы состояний (`SELECT ... FOR UPDATE` или оптимистический контроль конкурентного доступа с проверкой `version`) |
| NFR-003 | Время событий сохраняется в UTC; API использует ISO 8601; в интерфейсе отображается выбранная локальная зона |
| NFR-004 | Прикладные логи не содержат сырых токенов, паролей, ФИО пациентов и секретов |
| NFR-005 | Журнал аудита должен допускать только добавление записей на уровне сервисных операций; доступ на изменение/удаление ограничен на уровне БД |
| NFR-006 | Ошибки API имеют единый машиночитаемый контракт; некорректные переходы дают предсказуемый 409 конфликт |
| NFR-007 | Миграции схемы выполняются контролируемо; есть инструкция локального развертывания через Docker Compose |
| NFR-008 | Модульные, интеграционные тесты и тесты конкурентного доступа обязательны для ключевых инвариантов |
| NFR-009 | Демонстрационная система работает только с синтетическими данными; требования для реального использования требуют отдельной оценки безопасности и правовых аспектов |
| NFR-010 | Каждое действие имеет `request_id` для корреляции логов и событий аудита |

### Цели для последующей проверки производительности (не результаты тестирования)

- Пилотный стенд: ориентир 10 организаций, 100 сотрудников, до 10 000 демонстрационных образцов.
- Целевой p95 типовых API-запросов — до 500 мс на согласованном тестовом профиле без внешних интеграций; критерий пересматривается после замера.
- Данные не должны теряться при повторной передаче запросов и перезапуске обработчика. Для событий аудита гарантия обеспечивается транзакцией БД; для уведомлений требуется выбранная политика доставки/повторов.

## 7. Приёмочные / E2E сценарии

### AT-01 — Доставка без расхождений

**Дано:** три пробирки помещены в два контейнера партии, статус `READY_FOR_PICKUP`.
**Когда:** Отправитель подтверждает выдачу; Курьер подтверждает забор и затем доставку; Лаборатория подтверждает получение контейнеров, отмечает все три пробирки `ACCEPTED` и завершает приёмку.
**Тогда:** `COMPLETED`, в истории сохранены четыре независимых подтверждения двух передач.

### AT-02 — Недостача одной пробирки

**Дано:** в контейнере числятся три пробирки, но лаборатория обнаружила две.
**Когда:** две отмечены `ACCEPTED`, третья `MISSING` с причиной.
**Тогда:** `COMPLETED_WITH_ISSUES`; видны контейнер и конкретная отсутствующая пробирка.

### AT-03 — Отказ в приёмке

**Дано:** пробирка физически предъявлена лаборатории.
**Когда:** оператор ставит `REJECTED` с причиной и завершает проверку остальных пробирок.
**Тогда:** `COMPLETED_WITH_ISSUES`, причина сохранена.

### AT-04 — Недостаточно одной стороны

**Дано:** партия `READY_FOR_PICKUP`.
**Когда:** Отправитель подтвердил выдачу, Курьер ещё не подтвердил.
**Тогда:** `PICKUP_PENDING`, а не `IN_TRANSIT`. Аналогично `DELIVERY_PENDING` не означает `RECEIVING`.

### AT-05 — Авторизация подтверждений

**Дано:** ожидается подтверждение курьера.
**Когда:** Отправитель пытается подтвердить сам за курьера либо это делает чужой курьер.
**Тогда:** подтверждение отклонено, партия остаётся в текущем статусе.

### AT-06 — Конкурентное подтверждение

**Дано:** партия `PICKUP_PENDING`.
**Когда:** два одинаковых подтверждения приходят одновременно.
**Тогда:** не более одного перехода и одного события завершённой передачи; повторная попытка идемпотентна либо возвращает `409`.

### AT-07 — Нельзя назначить пробирку в два контейнера

**Дано:** пробирка уже в контейнере A.
**Когда:** её одновременно добавляют в контейнер B.
**Тогда:** БД предотвращает дублирование.

### AT-08 — Неполная приёмка и межорганизационный доступ

**Дано:** результат есть только для 4 из 5 пробирок; посторонний оператор знает ID партии.
**Когда:** Лаборатория пытается закрыть приёмку, а посторонний оператор — прочесть партию.
**Тогда:** обе операции запрещены; данные и состояние защищены.

## 8. Вне MVP / P1

- Планирование рейсов, оптимизация маршрутов, несколько курьеров на цепочке.
- Частичная успешная передача контейнеров, возврат, повторная перевозка, повреждения и температурные нарушения как самостоятельные исключения.
- Температурные сенсоры, нормативные диапазоны в зависимости от исследования и типа материала.
- Автоматизация регламентированных актов, интеграция с ЛИС, импорт/экспорт данных.
- Интеллектуальный анализ организационных инцидентов и обезличенных отчётов.
- Много-региональная конфигурация и полноценная система настроек на уровне субъектов РФ.

## 9. Дополнительные приёмочные проверки-сценарии v0.5

- **AT-09:** отсутствующий контейнер → DELIVERY_BLOCKED, ни одна пробирка автоматически не MISSING, ручное RETRY/CLOSE.
- **AT-10:** Лаборатория отклоняет контейнер → REJECTED с reason_code, частичного подтверждения доставки нет.
- **AT-11:** Руководитель лаборатории повторно открывает приёмку с причиной; прежняя история результатов не теряется.

- **AT-13:** прямой SQL UPDATE/INSERT/DELETE запечатанного манифеста отклоняется триггером в PostgreSQL.
- **AT-14:** зависшие передачи видны REGIONAL_OPERATIONS при недоступности Celery.
