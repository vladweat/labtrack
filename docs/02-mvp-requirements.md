# LabTrack — MVP Requirements (PRD/SRS)

**Версия:** 0.2 (черновик)  
**Приоритет:** `P0` — обязателен для первого демо; `P1` — после стабильного MVP.  
**Язык требований:** формулировка «система должна» означает проверяемое поведение.

## 1. Бизнес-процесс

1. Sender Operator регистрирует **каждую пробирку отдельно** как `Sample` с индивидуальной меткой.
2. Создаёт `Shipment`, добавляет в него один или несколько `TransportContainer` с собственными метками, распределяет пробирки между ними.
3. Назначает Courier и фиксирует неизменяемый манифест пробирок и контейнеров через `seal`.
4. **Передача отправитель → курьер**: Sender подтверждает выдачу (`PICKUP_PENDING`), назначенный Courier подтверждает получение (`IN_TRANSIT`).
5. **Передача курьер → лаборатория**: Courier подтверждает доставку (`DELIVERY_PENDING`), Lab Operator подтверждает получение контейнеров (`RECEIVING`).
6. Lab Operator проверяет пробирки **по одной**: `ACCEPTED`, `MISSING` (недостача) или `REJECTED` (отказ в приёмке); исключения требуют причины.
7. После явной обработки каждой пробирки партия закрывается как `COMPLETED` или `COMPLETED_WITH_ISSUES`; фиксируются события, доступна агрегированная статистика.

**Важно:** передача контейнера подтверждается двумя пользователями, но подтверждение контейнера само по себе **не** означает приёмку всех пробирок.

## 2. Функциональные требования P0

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-001 | Пользователь должен аутентифицироваться | Неавторизованные запросы к защищённым маршрутам отклоняются |
| FR-002 | Все операции должны проверять роль и организационный scope | Нельзя прочесть/изменить чужую партию подбором ID |
| FR-003 | Администратор организации управляет членством и ролями своих сотрудников | Операции за пределами своей организации отклоняются |
| FR-004 | Sender Operator регистрирует образец с уникальным непредсказуемым кодом | Совпадения кодов исключены ограничением БД, код не включает сведения о пациенте |
| FR-005 | Sender Operator создаёт черновик партии с одной организацией-отправителем и одной лабораторией назначения | Разные организации/лаборатории в одной партии недопустимы |
| FR-006 | Контейнеры и их пробирки можно добавлять, удалять и перемещать только в `DRAFT` | После seal манифест неизменяем |
| FR-007 | Одна пробирка не может находиться в двух контейнерах или партиях | `UNIQUE(container_items.sample_id)` защищает и при конкурентных запросах |
| FR-008 | `seal` фиксирует манифест контейнеров и пробирок | В партии ≥1 непустой контейнер, курьер назначен; после seal манифест неизменяем |
| FR-009 | Выдача курьеру требует двух подтверждений | Только после Sender + назначенного Courier партия переходит из `PICKUP_PENDING` в `IN_TRANSIT` |
| FR-010 | Получение контейнеров лабораторией требует двух подтверждений | Courier → `DELIVERY_PENDING`, Lab Operator адресной лаборатории → `RECEIVING` |
| FR-011 | Lab Operator фиксирует результат для **каждой пробирки** внутри контейнера | Только `ACCEPTED`, `MISSING`, `REJECTED`; два исключения требуют причину |
| FR-012 | Приёмка завершается только после явной отметки каждой позиции | Неотмеченные позиции препятствуют завершению |
| FR-013 | Итоговый статус партии различает доставку без/с расхождениями | `COMPLETED` — все `ACCEPTED`; иначе `COMPLETED_WITH_ISSUES` |
| FR-014 | Все значимые действия фиксируются в audit/event log | Для действия видны время, actor, объект, тип, причина и request_id |
| FR-015 | Операционный Dashboard показывает количества по статусам, просрочки и расхождения | Числа согласуются с транзакционными данными |
| FR-016 | Партия отменяется до начала двустороннего подтверждения выдачи | `CANCELLED` только из `DRAFT`/`READY_FOR_PICKUP`, с причиной |
| FR-017 | Повторная доставка команды не должна создавать повторную передачу или дублирующую партию | Поддерживается `Idempotency-Key` для критичных команд и/или безопасный retry по версии |
| FR-018 | Метки образца и контейнера содержат только случайные идентификаторы | Сканирование без авторизации не раскрывает внутренние сведения |

| FR-019 | Партия содержит 1..N маркированных контейнеров | В каждом контейнере ≥1 пробирка при seal; контейнер принадлежит ровно одной партии |
| FR-020 | Передачи требуют двух разных уполномоченных пользователей | Sender + назначенный Courier, затем тот же Courier + Lab Operator; самоподтверждение запрещено |
| FR-021 | Первый участник может отозвать ожидающую передачу до второго подтверждения | `withdraw_release`/`withdraw_delivery` журналируются и возвращают прежнее состояние |
| FR-022 | Сканирование контейнера не подтверждает автоматически все пробирки | Каждая пробирка должна быть отдельно отмечена на приёмке |
| FR-023 | В P0 допустимы только два типа исключений при приёмке | Недостача и отказ в приёмке пробирки, с указанием причины |

### Допущения MVP

- Каждая пробирка — отдельный `Sample`; пробирки объединяются в `TransportContainer`; партия содержит 1..N контейнеров. Повторные перевозки остаются за рамками.
- Два подтверждения — аутентифицированные действия пользователей, **не** юридически значимая электронная подпись. Подтверждение передачи контейнера не означает результатов приёмки его содержимого.
- Частичные передачи контейнеров, возвраты, отказ от целого контейнера/партии и отдельные процессы для иных инцидентов остаются за рамками P0.
- `expected_delivery_at` может задаваться при подготовке партии как операционный плановый срок, но не означает клинической пригодности.
- События фиксируются по факту действия пользователя; GPS-местоположение не вычисляется.
- В MVP приемка возможна с несколькими последовательными сканированиями в одной сессии `RECEIVING`; финализация — отдельное действие.

## 3. Права доступа P0 (упрощённо)

| Операция | Sender | Courier | Lab | Org Admin | Regional Analyst |
|---|---|---|---|---|---|
| Создать образец | Своя организация | — | — | — | — |
| Собрать контейнеры, запечатать партию и подтвердить выдачу | Своя организация | — | — | — | — |
| Просмотреть метаданные партии | Свои | Назначенные | Адресованные | Своя организация | Только агрегаты |
| Подтвердить получение и последующую доставку контейнеров | — | Назначенная партия | — | — | — |
| Подтвердить получение контейнеров, затем принять пробирки | — | — | Лаборатория назначения | — | — |
| Управлять ролями организации | — | — | — | Своя организация | — |
| Просмотреть агрегированную статистику | Своя организация | — | Своя лаборатория | Своя организация | Регион |

Роль `Organization Admin` **не обходит** по умолчанию ограничения на предметные операции. При необходимости сотруднику назначаются дополнительные роли. `Regional Analyst` не получает построчный доступ к сведениям об образцах.

## 4. Уведомления и фоновые задания

- `P0`: асинхронная обработка внутренних событий (например, уведомление о готовности/прибытии и о завершении с проблемами); сбой уведомления не отменяет основной переход.
- `P0`: периодический пересчёт/выявление опозданий относительно `expected_delivery_at` для незавершённых партий.
- `P0`: события бизнес-переходов фиксируются транзакционно, вместе с изменением состояния. Отправка сообщения во внешнюю систему не должна выполняться до коммита БД.
- `P1`: Email/Telegram/SMS, расширенные отчёты, интеграционные события и гарантированная доставка сообщений через transactional outbox (если появятся критичные интеграции).

## 5. Нефункциональные требования

| ID | Требование / решение |
|---|---|
| NFR-001 | PostgreSQL обеспечивает ссылочную целостность, уникальность и необходимые транзакционные блокировки |
| NFR-002 | Конкурирующие команды не должны обходить допустимые переходы состояний (`SELECT ... FOR UPDATE` или optimistic concurrency с проверкой `version`) |
| NFR-003 | Время событий сохраняется в UTC; API использует ISO 8601; в интерфейсе отображается выбранная локальная зона |
| NFR-004 | Прикладные логи не содержат сырых токенов, паролей, ФИО пациентов и секретов |
| NFR-005 | Audit log должен быть append-only на уровне сервисных операций; доступ на изменение/удаление ограничен на уровне БД |
| NFR-006 | Ошибки API имеют единый машиночитаемый контракт; некорректные переходы дают предсказуемый 409 Conflict |
| NFR-007 | Миграции схемы выполняются контролируемо; есть инструкция локального развертывания через Docker Compose |
| NFR-008 | Unit, integration и concurrency tests обязательны для ключевых инвариантов |
| NFR-009 | Демонстрационная система работает только с синтетическими данными; требования для реального использования требуют отдельного security/legal assessment |
| NFR-010 | Каждое действие имеет `request_id` для корреляции логов и audit events |

### Цели для последующей проверки производительности (не результаты тестирования)

- Пилотный стенд: ориентир 10 организаций, 100 сотрудников, до 10 000 демонстрационных образцов.
- Целевой p95 типовых API-запросов — до 500 мс на согласованном тестовом профиле без внешних интеграций; критерий пересматривается после замера.
- Данные не должны теряться при повторной передаче запросов и рестарте worker. Для событий аудита гарантия обеспечивается транзакцией БД; для уведомлений требуется выбранная политика доставки/повторов.

## 6. API: предварительный ресурсный контур

Это **не окончательный контракт**; конкретные payloads и коды будут разработаны после утверждения domain model:

- `/auth/*`, `/organizations`, `/organization-memberships`
- `/samples`, `/samples/{id}`
- `/shipments`, `/shipments/{id}`, `/shipments/{id}/containers`, `/shipments/{id}/containers/{container_id}/items`
- `/shipments/{id}/seal`
- `/shipments/{id}/handoffs/pickup/confirm-release`, `/shipments/{id}/handoffs/pickup/confirm-pickup`, `/shipments/{id}/handoffs/pickup/withdraw`
- `/shipments/{id}/handoffs/delivery/confirm-delivery`, `/shipments/{id}/handoffs/delivery/confirm-receipt`, `/shipments/{id}/handoffs/delivery/withdraw`
- `/shipments/{id}/receiving/items/{item_id}`, `/shipments/{id}/receiving/complete`
- `/shipments/{id}/cancel`, `/shipments/{id}/events`
- `/analytics/shipments/summary`

## 7. Acceptance / E2E сценарии

### AT-01 — Доставка без расхождений

**Given:** три пробирки помещены в два контейнера партии, статус `READY_FOR_PICKUP`.  
**When:** Sender подтверждает выдачу; Courier подтверждает pickup и затем delivery; Lab подтверждает получение контейнеров, отмечает все три пробирки `ACCEPTED` и завершает приёмку.  
**Then:** `COMPLETED`, в истории сохранены четыре независимых подтверждения двух передач.

### AT-02 — Недостача одной пробирки

**Given:** в контейнере числятся три пробирки, но лаборатория обнаружила две.  
**When:** две отмечены `ACCEPTED`, третья `MISSING` с причиной.  
**Then:** `COMPLETED_WITH_ISSUES`; видны контейнер и конкретная отсутствующая пробирка.

### AT-03 — Отказ в приёмке

**Given:** пробирка физически предъявлена лаборатории.  
**When:** оператор ставит `REJECTED` с причиной и завершает проверку остальных пробирок.  
**Then:** `COMPLETED_WITH_ISSUES`, причина сохранена.

### AT-04 — Недостаточно одной стороны

**Given:** партия `READY_FOR_PICKUP`.  
**When:** Sender подтвердил выдачу, Courier ещё не подтвердил.  
**Then:** `PICKUP_PENDING`, а не `IN_TRANSIT`. Аналогично `DELIVERY_PENDING` не означает `RECEIVING`.

### AT-05 — Авторизация подтверждений

**Given:** ожидается подтверждение курьера.  
**When:** Sender пытается подтвердить сам за курьера либо это делает чужой курьер.  
**Then:** подтверждение отклонено, партия остаётся в текущем статусе.

### AT-06 — Конкурентное подтверждение

**Given:** партия `PICKUP_PENDING`.  
**When:** два одинаковых подтверждения приходят одновременно.  
**Then:** не более одного перехода и одного события завершённого handoff; retry идемпотентен либо возвращает `409`.

### AT-07 — Нельзя назначить пробирку в два контейнера

**Given:** пробирка уже в контейнере A.  
**When:** её одновременно добавляют в контейнер B.  
**Then:** БД предотвращает дублирование.

### AT-08 — Неполная приёмка и межорганизационный доступ

**Given:** результат есть только для 4 из 5 пробирок; посторонний оператор знает ID партии.  
**When:** Lab пытается закрыть приёмку, а посторонний оператор — прочесть партию.  
**Then:** обе операции запрещены; данные и состояние защищены.

## 8. Вне MVP / P1

- Планирование рейсов, оптимизация маршрутов, несколько курьеров на цепочке.
- Частичная передача/отказ в приёмке целого контейнера, возврат, повторная перевозка, повреждения и температурные нарушения как отдельные исключения.
- Температурные сенсоры, нормативные диапазоны в зависимости от исследования и типа материала.
- Автоматизация регламентированных актов, интеграция с ЛИС, импорт/экспорт данных.
- Интеллектуальный анализ организационных инцидентов и обезличенных отчётов.
- Много-региональная конфигурация и полноценная система настроек на уровне субъектов РФ.
