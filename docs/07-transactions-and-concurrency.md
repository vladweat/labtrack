## 1. Граница ответственности

`Shipment` — **агрегат и единица сериализации**. Его состояние, контейнеры, включённые пробирки, передачи и итоговая приёмка изменяются через единый слой команд/сервисов. Веб-обработчики не выполняют прямые изменения статуса ORM-моделей.

- `DRAFT` допускает изменение контейнеров и их содержимого.
- После `seal` манифест фиксируется: 1..N непустых контейнеров, каждая пробирка в одном контейнере.
- Передачи — **по всей партии и манифесту контейнеров**, отдельные подтверждения разных пользователей.
- Получение контейнеров в лаборатории открывает `RECEIVING`, **но не подтверждает ни одной пробирки**.
- Только результаты каждой пробирки — `ACCEPTED`, `MISSING`, `REJECTED` — определяют итог партии.
- Изолированные по организациям пользователи видят только разрешённые ресурсы; `REGIONAL_ANALYST` читает только агрегаты.

## 2. Автомат состояний партии v0.5

Полный автомат состояний Mermaid и условия переходов зафиксированы в [Уточнение доменных правил](10-domain-hardening-v05.md) и [Доменная модель](03-domain-and-workflows.md).

К базовым переходам добавлены:
- `IN_TRANSIT/DELIVERY_PENDING → DELIVERY_BLOCKED` при `MISSING`/`REJECTED` контейнера; если передача доставки Handoff имела статус PENDING, он атомарно меняется на WITHDRAWN;
- `DELIVERY_BLOCKED → IN_TRANSIT` при ручном RETRY_DELIVERY региональной операционной ролью (новая попытка доставки);
- `DELIVERY_BLOCKED → CLOSED_UNDELIVERED` при ручном CLOSE_UNDELIVERED;
- `COMPLETED/COMPLETED_WITH_ISSUES → RECEIVING` только по LAB_MANAGER с причиной и новым сеансом приёмки.

Ни один контейнерный инцидент не присваивает результатов `container_items` автоматически. Исключения по пробиркам остаются только `MISSING`/`REJECTED`, но теперь требуют `reason_code`.

| Сценарий использования | Атомарные изменения под блокировкой Shipment |
|---|---|
| Сообщение о проблеме контейнера | Создать container_issue со статусом OPEN, отозвать ожидающую передачу доставки при её наличии, установить статус DELIVERY_BLOCKED, добавить аудит |
| Разрешение блокировки партии | Разрешить/закрыть все проблемы OPEN, установить IN_TRANSIT или CLOSED_UNDELIVERED, добавить аудит |
| Повторное открытие приёмки | Создать новый сеанс приёмки OPEN, изменить конечный результат на RECEIVING, добавить аудит |
| Исправление результата пробирки | Сохранить новый текущий результат, неизменяемую receipt_revision и аудит; только сеанс OPEN |
| Синхронизация команды курьера | Резервирование идемпотентности, блокировка Shipment, передача, аудит и ответ одной транзакцией |

## 3. Передача Handoff: точные условия

### Забор

1. Отправитель выполняет `confirm_release`, сверив все контейнеры манифеста; создаётся `handoff(kind=PICKUP,status=PENDING)`.
2. Курьер считывает метки контейнеров и подтверждает получение **того же состава**. Только этот шаг переводит партию в `IN_TRANSIT`.
3. Самоподтверждение запрещено, даже если пользователь состоит сразу в двух ролях. К моменту каждого действия проверяем активный аккаунт и членство.
4. Отправитель может отозвать своё ожидающее подтверждение до действия курьера; история сохраняется. Следующая попытка получает новый `attempt_no`.

### Доставка

1. Курьер предъявляет контейнеры и выполняет `confirm_delivery`.
2. Оператор лаборатории из организации назначения сверяет контейнеры, выполняет `confirm_receipt`.
3. Только после этого партия переходит в `RECEIVING` и становится доступна приёмка пробирок.
4. Курьер может отозвать ожидающее подтверждение до действия лаборатории.

**Практическое условие:** каждый участник в интерфейсе сканирует/явно сверяет полный набор кодов контейнеров из запечатанного манифеста. API принимает список кодов/ID подтверждённых контейнеров и сравнивает его как **множество** с ожидаемым набором (без дубликатов). Это защита от случайного подтверждения неверного контейнера, но не криптографическое доказательство физической передачи.

Частичная **успешная** передача в P0 не поддерживается. Если контейнер отсутствует или отклонён, **второй участник не подтверждает передачу**; создаётся ContainerIssue, партия переходит в DELIVERY_BLOCKED для ручного разрешения. Это не успешная доставка.

## 4. Приёмка одной пробирки

| Значение | Физически предъявлена? | Причина | Что означает |
|---|---|---|---|
| `ACCEPTED` | Да | Не нужна | Организационно принята лабораторией |
| `MISSING` | Нет | Обязательна | По манифесту должна быть, но не обнаружена |
| `REJECTED` | Да | Обязательна | Лаборатория отказала в приёмке конкретной пробирки |

Сканирование контейнера только открывает список ожидаемых пробирок; результат по каждой позиции фиксируется отдельно. В `RECEIVING` допускается исправление ошибочной отметки с `receipt_revision` и аудитом. После финализации прямое изменение запрещено, но **LAB_MANAGER может повторно открыть приёмку** с новым сеансом приёмки, после чего изменения снова возможны с полной историей.

Отказ в приёмке пробирки — операционное решение сотрудника, не автоматическая клиническая оценка. Отдельных категорий «повреждена», «температура нарушена», «возвращена» и т. п. в P0 нет. Причины `MISSING`/`REJECTED` — обязательные коды из справочника для области доступа и категории, свободный комментарий необязателен.

## 5. Блокировки, порядок и изоляция

**Рекомендация:** PostgreSQL `READ COMMITTED` + короткие транзакции + последовательный `SELECT ... FOR UPDATE` на `shipments` для каждой команды, меняющей агрегат.

Для вложенных изменений всегда соблюдаем порядок:

1. `shipments` (одна строка, `FOR UPDATE`);
2. связанные `transport_containers` / `container_items` или `handoffs`;
3. `audit_events` и `idempotency_records` в той же транзакции.

Запрещаем любые отдельные пути исполнения, которые сначала блокируют позицию или передачу, а затем партию — это создаст риск взаимной блокировки.

~~~python
async def execute_shipment_command(
    session: AsyncSession,
    shipment_id: UUID,
    actor: Actor,
    command: Command,
) -> CommandResult:
    # Псевдокод: детали хранилища/политик зададим в API design.
    # Транзакция открыта на уровне use-case; внутри не делать HTTP/LLM/Celery вызовы.
    shipment = await repository.get_for_update(session, shipment_id)
    policies.require_allowed(actor, command, shipment)
    command.validate_state(shipment)
    result = await command.apply(session, shipment)
    await audit_repository.append(session, result.event)
    shipment.version += 1
    return result
~~~

> Псевдокод показывает распределение ответственности за инварианты. Реальный код должен также атомарно обрабатывать идемпотентность и ошибки уникальности. Не использовать `with_for_update()` вне активной транзакции.

**Почему не SERIALIZABLE везде:** для небольшого модульного монолита блокировку строки агрегата проще тестировать; достаточно для корректного запечатывания/забора/доставки/приёмки при дисциплине единого пути записи. Оставляем `UNIQUE(sample_id)` как последнюю линию защиты, если две разные партии одновременно включают одну пробирку.

## 6. Транзакционные границы по сценариям использования

| Сценарий использования | В одной транзакции | Что делать после фиксации транзакции |
|---|---|---|
| Регистрация пробирки | Валидация, INSERT пробирки, аудит | Ничего обязательного |
| Редактирование манифеста | Заблокировать партию; проверки; INSERT/DELETE container_item; увеличить версию; аудит | Асинхронная обработка не нужна |
| Запечатывание | Заблокировать партию; проверка всех контейнеров и пробирок; установить status/sealed_at/version; аудит | Уведомление курьера без гарантии доставки |
| Начало/подтверждение/отзыв передачи | Заблокировать партию; роль, исполнитель, манифест, попытка передачи, статус, версия, аудит | Без гарантии доставки уведомление другой стороны |
| Запись/исправление приёмки | Заблокировать партию; проверка пробирки и текущей приёмки; поля приёмки; аудит; версия | Обновить UI |
| Завершение приёмки | Заблокировать партию; COUNT необработанных=0; результат; status/completed_at/version; аудит | Без гарантии доставки статистика/уведомление |
| Отмена | Заблокировать партию; status/cancel_reason/version; аудит | Без гарантии доставки уведомление |

**Никогда** не подтверждать статус, если запись аудита не сохранилась; обе операции должны откатываться вместе. Если уведомление отправляется через Celery сразу до фиксации транзакции, обработчик может увидеть ещё несуществующее состояние: запускать только после успешной фиксации транзакции. Без транзакционной таблицы исходящих событий P0 уведомления без гарантии доставки: при падении процесса между фиксацией транзакции и публикацией сообщение может быть потеряно. Для критичных интеграций потребуется таблица исходящих событий (P1).

## 6.1. Единый порядок блокировок v0.5

Для **всех** команд, включая синхронизацию курьера: аутентификация/проверка структуры → транзакционное резервирование `Idempotency-Key` (если требуется) → `SELECT FOR UPDATE` на партию → дочерние строки → аудит + сохранённый ответ → фиксация транзакции. Не допускаем обратного порядка `Shipment → idempotency` или `child → Shipment`. Ключи, совпадающие у разных параллельных запросов, сериализуются уникальным индексом; изменение ролей проверяется до выдачи кэшированного ответа.

**Триггеры манифеста:** PostgreSQL сериализует прямую модификацию контейнеров/их состава с запечатыванием, блокируя родительскую партию. Версия манифеста `manifest_revision` фиксируется после запечатывания, не равна изменяющемуся `shipment.version`.

## 7. Идемпотентность и обработка конфликтов

Для создания, запечатывания, подтверждений, отмены и финализации используем заголовок `Idempotency-Key`. Ключ включает область доступа: исполнитель + операция, а данные запроса сравниваются по каноническому хэшу запроса.

**Упрощённый алгоритм:**

1. В рамках той же транзакции БД зарезервировать строку `idempotency_records` через INSERT с уникальностью `(actor_id,operation,key)`.
2. Если ключ уже существует, дождаться завершения конкурирующей транзакции, сверить хэш запроса и возвратить сохранённый HTTP ответ; различающиеся данные запроса → `409`.
3. Если запись новая, выполнить команду под блокировкой `shipment`; сохранить response_status/response_body и аудит, затем зафиксировать транзакцию.
4. Только после фиксации транзакции ответить клиенту и публиковать без гарантии доставки уведомления.

Если транзакция падает до фиксации транзакции, и идемпотентная запись, и бизнес-изменение откатываются. Идемпотентность с разными ключами **не** обещает одинаковый результат: корректность в этом случае обеспечивают блокировки, автомат состояний и ограничения уникальности. TTL записи предлагается 24 часа в демонстрации и требует документирования в API; после TTL повтор создания может создать новый объект, поэтому клиент обязан соблюдать политику повторных попыток.

**Ошибки:**

| Ситуация | Ответ |
|---|---|
| Другая организация / отсутствие области доступа | `403` или `404` по выбранной политике |
| Некорректный переход/необработанная пробирка | `409 Conflict`, стабильный код ошибки |
| Пробирка уже в контейнере | `409 SAMPLE_ALREADY_ASSIGNED` (обработать PostgreSQL `23505` на известном ограничении уникальности) |
| Одинаковый ключ, другие данные запроса | `409 IDEMPOTENCY_KEY_REUSED` |
| Ошибочная структура запроса | `422` |
| Временная недоступность БД | `503` или контролируемый `500`, без утечки деталей и с корреляционным идентификатором запроса |

## 8. Границы безопасности и аудит

- Границы проверяются для **каждого** чтения и записи: организация отправителя, организация назначения, назначенный Курьер либо региональный аналитик в своей области доступа.
- Курьер не получает данные других партий; аналитик получает агрегаты, не строки `samples`/`container_items`.
- Не отдавать SQL-ошибки клиенту; запросы параметризованы ORM/драйвером, не конструировать фильтры из необработанных SQL-фрагментов.
- `AuditEvent` имеет `request_id`, идентификатор объекта, исполнителя/время и минимальные безопасные данные подробностей. Пароли, токены, диагнозы, пациентские идентификаторы и PHI не логируются.
- События `RELEASE_CONFIRMED` / `PICKUP_CONFIRMED` / `DELIVERY_CONFIRMED` / `LAB_RECEIPT_CONFIRMED` различны; аудит отображает обе стороны.
- Подтверждения не являются квалифицированной подписью и не заменяют регламентированные перевозочные документы.

## 9. Минимальный набор интеграционных тестов и тестов конкурентного доступа

| Идентификатор | Тест | Ожидание |
|---|---|---|
| TX-01 | Два запроса добавляют одну пробирку в разные контейнеры | Одна вставка, вторая `409`; не более одной записи container_item |
| TX-02 | `seal` одновременно с изменением состава | Либо изменение до запечатывания отражено в манифесте, либо изменение отклонено; «полуманифеста» нет |
| TX-03 | Забор подтверждает только Отправитель | `PICKUP_PENDING`, Курьер ещё не владелец |
| TX-04 | Назначенный Курьер и посторонний Курьер подтверждают одновременно | Только назначенный пользователь может завершить передачу |
| TX-05 | Один аккаунт с двумя ролями подтверждает обе стороны | Вторая операция запрещена |
| TX-06 | Повтор подтверждения с тем же Idempotency-Key | Один переход, одна подтверждённая попытка, тот же ответ |
| TX-07 | Курьер подтверждает доставку, Лаборатория ещё нет | `DELIVERY_PENDING`; приёмка пробирок закрыта |
| TX-08 | Лаборатория подтверждает контейнеры и пытается автоматически принять все пробирки | Не принимаются автоматически; `receipt_result` остаётся NULL |
| TX-09 | 1 из N пробирок не имеет результата | Финализация отклонена, аудит не содержит фиктивного завершения |
| TX-10 | Есть `MISSING` и `REJECTED`, у обоих причина | Партия завершается `COMPLETED_WITH_ISSUES` |
| TX-11 | Причина пустая для `MISSING`/`REJECTED` | CHECK/проверка отклоняет |
| TX-12 | Внутри транзакции падает запись аудита | Статус и передача откатываются |
| TX-13 | Две финализации одновременно | Не более одного события завершения |
| TX-14 | Отправитель из организации A читает/изменяет партию B | Доступ запрещён без утечки содержимого |
| TX-15 | Ожидающая передача отозвана и создана повторно | Старая WITHDRAWN, новый `attempt_no`, не два активных |
| TX-16 | После запечатывания пытаются добавить контейнер или пробирку | Конфликт; ни одна запись не изменилась |
| TX-17 | Повторная команда после сбоя соединения в момент фиксации транзакции | Результат однозначно восстанавливается по Idempotency-Key |
| TX-18 | Данные одной области переданы в партию другой области | FK или валидация отклоняет |

**Практика:** использовать настоящий PostgreSQL для интеграционных тестов и тестов конкурентного доступа; SQLite не повторяет нужную семантику блокировок строк. Для одновременных операций нужны отдельные сессии/соединения и синхронизированный старт. Модульные тесты покрывают политики и автомат состояний без БД, E2E — сквозной сценарий 10 пробирок в 2 контейнерах.
