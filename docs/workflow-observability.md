# Наблюдаемость рабочих процессов

LabTrack записывает небольшой набор событий рабочего процесса с ограниченным числом возможных значений полей через существующий механизм журналирования JSON. В этом репозитории нет зависимости от Prometheus или конечной точки метрик. События доступны в журналах процессов API и фонового обработчика; панели мониторинга нужен существующий сборщик журналов JSON, который этот репозиторий не развёртывает и не настраивает.

## События

| Событие (`message`) | Значение | Поля с ограниченным набором значений |
|---|---|---|
| `offline_sync_command` | Один серверный результат для одной офлайн-команды курьера | `command_type=pickup|delivery`, `outcome=applied|replayed|rejected|retryable|review_required`, `reason_category`, `count=1` |
| `custody_command_failure` | Ошибка известной конечной точки, изменяющей состояние передачи ответственности | `command_type`, определяемое статусом поле `reason_category`, `count=1` |
| `stalled_notification_scan_completed` | Проверка уведомлений и количество задержанных заборов и доставок, превысивших порог | `candidate_case_count`, `notification_insert_count`, `notification_dedup_count`, `stalled_pickup_count`, `stalled_delivery_count`, `duration_ms` |
| `stalled_notification_scan_failed` | Ошибка существующей проверки уведомлений; задача по-прежнему возбуждает исключение для повторной попытки Celery и видимости ошибки | `outcome=failure`, `error_type` |
| `stalled_work_count_failed` | Ошибка отдельного агрегирующего запроса только для чтения по задержанным работам; сохранение уведомлений остаётся зафиксированным | `error_type` |

Результаты офлайн-событий отражают реализованные результаты: `APPLIED` преобразуется в `applied`, `ALREADY_APPLIED` — в `replayed`, а существующие значения `REJECTED`, `RETRYABLE` и `REVIEW_REQUIRED` приводятся к нижнему регистру. Офлайн-синхронизация не возвращает результат `CONFLICT`, поэтому он не добавлен искусственно. Отклонение из-за устаревшего состояния учитывается как `rejected` с `reason_category=stale_state`.

Категории причин ошибок передачи ответственности определяются только HTTP-статусом: `authorization`, `missing_or_hidden`, `conflict`, `validation`, `rate_limited`, `server_error` или `request_error`. Офлайн-категории используют фиксированные внутренние соответствия кодов причин и никогда не выводят исходные коды или сообщения ошибок.

Поля забора и доставки подсчитывают текущие случаи, превысившие настроенные пороги задержки (по умолчанию четыре часа). Они вычисляются существующим общим SQL-запросом задержанных случаев в периодической задаче Celery, сейчас по умолчанию каждые пять минут. Они не подсчитывают всю ожидающую работу, не требуют получателя уведомления и не меняют состояние передачи ответственности. Запрос подсчёта выполняется после фиксации вставки уведомлений и вне обработки запросов API. При его ошибке проверка записывает `stalled_work_count_failed`; уведомления остаются успешно сохранёнными.

Все поля событий используют фиксированные перечисления или числовые значения. События не содержат идентификаторов пациентов, пробирок, контейнеров, партий, пользователей, организаций или регионов; в них нет адресов электронной почты, свободного текста, данных документов, токенов доступа или исходных URL. Стандартный журнал запросов также включает сгенерированный сервером `request_id` для контролируемого сопоставления записей. Сохраняйте его как обычное поле журнала: **не превращайте `request_id`, данные маршрута или другие значения отдельных запросов в метки метрик или индексируемые метки**. Индексируйте только приведённые выше поля с ограниченным набором значений. Применяйте обычные для платформы журналирования ограничения доступа и сроки хранения ко всем журналам приложения.

## Пример панели мониторинга и оповещений

Это иллюстративные запросы Loki LogQL. Их синтаксис следует официальным [руководству по запросам LogQL](https://grafana.com/docs/loki/latest/query/) и [справочнику запросов метрик](https://grafana.com/docs/enterprise-logs/latest/query/metric_queries/). Замените метку потока `service` на метку вашего сборщика; этот репозиторий не развёртывает Loki, панели мониторинга или оповещения.

Частота офлайн-команд по результату и причине с ограниченным набором значений за последние пять минут:

```logql
sum by (command_type, outcome, reason_category) (
  count_over_time(
    {service="labtrack-api"}
      | json
      | message="offline_sync_command"
      [5m]
  )
)
```

Ошибки передачи ответственности за пятнадцать минут:

```logql
sum by (command_type, reason_category) (
  count_over_time(
    {service="labtrack-api"}
      | json
      | message="custody_command_failure"
      [15m]
  )
)
```

Последний замер количества задержанных работ, превысивших порог, за последние десять минут:

```logql
max by (service) (
  last_over_time(
    {service="labtrack-worker"}
      | json
      | message="stalled_notification_scan_completed"
      | unwrap stalled_pickup_count
      [10m]
  )
)
```

Используйте тот же запрос с `unwrap stalled_delivery_count` для доставки. Полезная начальная панель мониторинга содержит результаты офлайн-команд, ошибки передачи ответственности и два счётчика задержанных работ. Рассмотрите вызов или уведомление оператора, когда:

- у периодической проверки нет события завершения более двух ожидаемых интервалов (10 минут при стандартном интервале пять минут) либо она многократно выдаёт `stalled_notification_scan_failed`;
- возникает `stalled_work_count_failed`, поскольку данные о количестве задержанных работ недоступны, даже если уведомления успешно добавлены;
- количество задержанных заборов или доставок остаётся ненулевым несколько проверок подряд либо офлайн-результаты `review_required` требуют оперативного рассмотрения.

Считайте это сигналами для расследования, а не целевыми показателями уровня обслуживания. Ненулевое число задержанных работ не должно вызывать автоматическое подтверждение, отзыв, закрытие или иное изменение состояния передачи ответственности. `replayed` — ожидаемое поведение идемпотентности и само по себе не должно вызывать срочное оповещение.

## Инструкция оператору

1. Найдите соответствующее событие `offline_sync_command`, `custody_command_failure` или проверки фонового обработчика. Агрегируйте только по полям события с ограниченным набором значений.
2. Для одного запроса API сопоставьте записи журналов приложения по сгенерированному сервером `X-Request-ID`. Не используйте идентификаторы ресурсов или запросов как метки панели мониторинга.
3. Для задержанного случая изучите представление `GET /api/v1/operations/stalled-shipments` с проверкой доступа. Оно читает достоверное состояние PostgreSQL и не зависит от доставки входящих уведомлений. Следуйте существующим проверкам ролей и процедуре эскалации рабочего процесса; не меняйте состояние только на основании счётчика.
4. Если проверка уведомлений завершается ошибкой, проверьте состояние фонового обработчика Celery, Beat и Redis, затем подключение к PostgreSQL. Доставка входящих уведомлений не гарантируется; используйте представление операций как источник текущих задержанных случаев.
5. Если появляется только `stalled_work_count_failed`, изучите ошибки подключения фонового обработчика к БД или выполнения запроса и убедитесь, что следующая проверка восстанавливает оба поля счётчиков. Этот агрегат не зависит от сохранения уведомлений.

Примеры запросов предполагают наличие платформы агрегации журналов с поддержкой JSON и не проверены на развёрнутом сборщике. Без него изучайте локальные журналы Compose или существующие журналы процессов развёртывания; в репозитории нет настройки долговременного хранения журналов, панели мониторинга или оповещений.
