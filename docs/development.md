# Локальная разработка

## Требования

- Python 3.12
- Node.js 22.13+ в линейке Node 22 и npm 10
- Docker Compose

Используйте `.env.example` только для локальной разработки и задайте локальные значения до запуска Compose. Не используйте их вне своей машины.

## Инфраструктура

Для API и основного рабочего процесса достаточно PostgreSQL. Из корня репозитория:

```bash
test -f .env || cp .env.example .env
docker compose up -d postgres
```

Compose также описывает Redis, фоновый обработчик и Beat для фоновых уведомлений без гарантии доставки; они не нужны для локального входа или основного рабочего процесса.

## Серверная часть

Из `backend/` установите зависимости, примените миграции и запустите API:

```bash
cd backend
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
alembic upgrade head
uvicorn app.main:app --reload --host 127.0.0.1 --port 8000 --no-proxy-headers
```

API доступен на `http://127.0.0.1:8000`; интерактивная схема — `/docs`. Аккаунты и назначения прав с ограниченной областью доступа настраиваются оператором через CLI из `backend/`, публичного API администрирования нет. Примеры CLI и настройки ролей: [руководство серверной части](../backend/README.md).

## Веб-клиент

В отдельном терминале:

```bash
cd web
npm ci
npm run dev
```

Vite перенаправляет `/api/v1` к локальной серверной части. Команда `npm run check` выполняет проверку стиля веб-клиента, модульные проверки, сборку TypeScript и браузерные проверки. Отдельная локальная приёмочная проверка браузера и API запускается командой `npm run test:acceptance:local`; это отдельный сценарий с одноразовой PostgreSQL.

### Сквозная приёмочная проверка: отправитель → курьер → лаборатория

Этот сценарий с реальным браузером и API запускает FastAPI и Vite локально и проверяет
сценарий на новой синтетической PostgreSQL. Он не подключается к внешней или
демо-БД. Скрипт создаёт контейнер `postgres:15` без сети и опубликованных
портов, использует сокет Unix и удаляет контейнер, сокет и временные файлы
через `trap`. Образ PostgreSQL должен быть заранее скачан: сам скрипт никогда
не выполняет `docker pull`.

На Linux установите зависимости и запустите сценарий из корня репозитория:

```bash
cd backend
python3.12 -m venv .venv
.venv/bin/python -m pip install -e '.[dev]'
cd ../web
npm ci
npx playwright install --with-deps chromium
docker pull postgres:15
npm run test:acceptance:local
```

Скрипт сам использует `backend/.venv/bin/python`, `web/node_modules` и кешированный
браузер. Для нестандартных путей задайте `LABTRACK_PYTHON_BIN` и
`LABTRACK_WEB_NODE_MODULES`. При сбое локальный запуск показывает этап, где
остановился сценарий запуска, а затем диагностические сообщения Playwright и API со
скрытием сгенерированных адресов электронной почты и паролей. Для проверки пропущенных зависимостей
сначала убедитесь, что доступны Docker, Python 3.12, Node 22, Chromium и образ
`postgres:15`. В CI вывод сценария намеренно скрыт, а артефакты не загружаются;
выделенный процесс CI `.github/workflows/real-acceptance.yml` запускает эту же
команду на соответствующих PR. Если задание CI завершается ошибкой, повторите
команду локально, чтобы изучить диагностику. Не публикуйте непроверенные логи:
они могут содержать синтетические идентификаторы или тела ответов.

Дополнительные команды и поведение PWA описаны в [руководстве веб-клиента](../web/README.md). Перед использованием новых локальных данных проверьте синтетическую границу в [данных и целостности](data-and-integrity.md).

Локальная проверка резервного копирования и восстановления синтетической PostgreSQL, её ограничения и точные
команды описаны в [руководстве по резервному копированию и восстановлению](backup-restore.md). Она требует
отдельную демонстрационную песочницу и не касается публичного демонстрационного стенда.
