# LabTrack v0.5 — API Contract Delta

> **Исторический документ (до v0.6).** Приоритет имеют [Decisions v0.6](15-decisions-v06.md), [Domain v0.6](16-domain-workflows-v06.md), [Data Model v0.6](17-data-model-v06.md), [API v0.6](18-api-v06.md). Этот текст может содержать устаревшие all-or-nothing handoff и unilateral resolution; не использовать его как актуальный контракт.

**Base path:** `/api/v1` · **Status:** design-first, not implemented.  
**Machine-readable:** [OpenAPI 3.1 JSON](../openapi/labtrack-v1.json) (v0.5 draft). This document overrides contradictory rules in the original [REST API v0.4](09-api-specification.md).

## 1. Unchanged principles

- Authentication with Argon2id password hashes and short-lived Bearer JWT. Every operation checks current actor and organization/region scope; UUID or QR never authorize access by themselves.
- One `Sample` per physical tube, inside exactly one `TransportContainer`; a Shipment groups containers. The manifest becomes immutable at seal.
- A handoff needs **two different authenticated people**: Sender + assigned Courier, then Courier + destination Lab Operator. A confirmed container handoff is **not** per-tube acceptance.
- Sample outcomes are `ACCEPTED`, `MISSING`, `REJECTED`; container issues use `MISSING` or `REJECTED`. Both exception kinds require structured reason codes.
- Write commands are atomic with audit and idempotency. P0 notifications remain best-effort.

## 2. Changed / added routes

| Method | Route | Authorized role | Request | Success / effect |
|---|---|---|---|---|
| `GET` | `/issue-reasons?scope=SAMPLE&kind=REJECTED` | Sender/Courier/Lab within their scope | filter scope/kind | 200 list active reason codes |
| `POST` | `/shipments/{id}/container-issues` | Assigned Courier or destination Lab Operator (REJECTED only Lab) | `{container_id,kind,reason_code,comment?}` | 201; IN_TRANSIT/DELIVERY_PENDING → DELIVERY_BLOCKED |
| `GET` | `/shipments/{id}/container-issues` | Scoped participant / REGIONAL_OPERATIONS region | — | 200 list issues |
| `POST` | `/shipments/{id}/container-issues/resolve` | REGIONAL_OPERATIONS same region | `{resolution,reason}` | 200; RETRY_DELIVERY → IN_TRANSIT or CLOSE_UNDELIVERED → CLOSED_UNDELIVERED |
| `POST` | `/shipments/{id}/receiving/reopen` | LAB_MANAGER of destination | `{reason}` | 200; COMPLETED* → RECEIVING with new receiving session |
| `GET` | `/shipments/{id}/receiving/history` | Scoped destination Lab or Sender (read-only) | pagination | 200 receiving sessions + receipt revisions |
| `GET` | `/samples/{id}/external-references` | Sender origin or destination Lab when assigned | — | 200 scoped opaque references |
| `POST` | `/samples/{id}/external-references` | Sender origin | `{system_code,reference_kind,external_id}` | 201, synthetic opaque references only |
| `GET` | `/courier/shipments/{id}/offline-manifest` | Assigned Courier | — | 200 signed-in scoped offline manifest snapshot (no patient information) |
| `POST` | `/courier/sync` | Assigned Courier with currently active membership | `{commands:[...]}` | 200 per-command APPLIED/ALREADY_APPLIED/REJECTED/RETRYABLE |
| `GET` | `/operations/stalled-shipments` | REGIONAL_OPERATIONS | filter region / age / status | 200 queryable pending/delivery-blocked cases (no row-level sample data) |

`/shipments/{id}/receiving/items/{item_id}` **changes request schema**:

```json
{"result":"MISSING","reason_code":"SAMPLE_NOT_FOUND","comment":"QR не обнаружен при сверке"}
```

For ACCEPTED, both `reason_code` and `comment` must be absent or null. For MISSING and REJECTED, `reason_code` is required and must be active for `scope=SAMPLE,kind=result`; comment optional, trim, max 500 chars. This replaces the old free-text `reason` field in receiving commands.

`Shipment.status` adds DELIVERY_BLOCKED and CLOSED_UNDELIVERED. A completed Shipment can return to RECEIVING only via a scoped lab-manager reopen command; no other successful terminal status can be altered by ordinary users.

## 3. Container issue example

Request:

```http
POST /api/v1/shipments/33333333-3333-4333-8333-333333333333/container-issues
Authorization: Bearer <token>
Idempotency-Key: 95959595-9595-4595-8595-959595959595
Content-Type: application/json

{
  "container_id":"44444444-4444-4444-8444-444444444444",
  "kind":"REJECTED",
  "reason_code":"CONTAINER_SEAL_UNACCEPTABLE",
  "comment":"Описание операционного отказа"
}
```

Response 201:

```json
{
  "issue": {
    "id":"55555555-5555-4555-8555-555555555555",
    "container_id":"44444444-4444-4444-8444-444444444444",
    "kind":"REJECTED",
    "status":"OPEN",
    "reason_code":"CONTAINER_SEAL_UNACCEPTABLE"
  },
  "shipment_id":"33333333-3333-4333-8333-333333333333",
  "shipment_status":"DELIVERY_BLOCKED"
}
```

A container `REJECTED` issue requires a destination Lab Operator or Lab Manager. A missing container may be reported by Courier or destination Lab Operator. The server validates container membership in the sealed manifest even if the container physically was not presented.

In the same transaction: create issue; withdraw any PENDING Delivery handoff with a reason and `withdrawn_by`; move Shipment to DELIVERY_BLOCKED; append audit. All sample results remain unchanged and receiving is not allowed.

**No partial success:** other containers do not count as delivered; second party does not confirm the blocked handoff.

## 4. Manual resolution

Request:

```json
{"resolution":"RETRY_DELIVERY","reason":"Контейнер найден и доступен для повторной передачи"}
```

Or `{"resolution":"CLOSE_UNDELIVERED","reason":"Фактическая доставка не состоялась"}`.

- Only REGIONAL_OPERATIONS in the same region.
- Requires Shipment DELIVERY_BLOCKED, at least one relevant issue, no contradictory pending receiving session.
- Resolves/closes **all OPEN container issues** with actor + reason and changes Shipment atomically.
- RETRY_DELIVERY → IN_TRANSIT; next Delivery handoff is a *new attempt* with a different `attempt_no`.
- CLOSE_UNDELIVERED → CLOSED_UNDELIVERED, records `closed_at/closed_by/closure_reason`; never counted as delivered or complete.
- No automatic transfer of physical ownership or legal responsibility is implied. The physical disposition of refused containers needs an operational policy before real-world pilot.

## 5. Receiving reopen and history

Request:

```http
POST /api/v1/shipments/33333333-3333-4333-8333-333333333333/receiving/reopen
Authorization: Bearer <token>
Idempotency-Key: ccccccdd-cccc-4ccc-8ccc-cccccccccccc
Content-Type: application/json

{"reason":"При проверке выявлена ошибочная отметка пробирки"}
```

- Only LAB_MANAGER at destination, for COMPLETED/COMPLETED_WITH_ISSUES and only if a previous CLOSED receiving session exists.
- Same transaction: lock Shipment, create next OPEN receiving session, move status to RECEIVING, append audit, bump version.
- Existing latest `container_items.receipt_result` stays unchanged; edits within the session append `receipt_revisions`. No reset to null.
- Closing the session re-checks all items and derives COMPLETED / COMPLETED_WITH_ISSUES. Old session and audit remain visible in history.
- Only one OPEN session; concurrent reopen attempts serialize and one receives 409 unless same idempotency key.

Receiving history is ordered chronologically and scoped. Expose `changed_by` and `changed_at`, but never credentials, raw patient records, or unneeded security data.

## 6. Courier offline contract

**Offline manifest response:**

```json
{
  "shipment_id":"33333333-3333-4333-8333-333333333333",
  "manifest_revision":4,
  "status":"PICKUP_PENDING",
  "container_codes":["LT-C-EXAMPLE-01","LT-C-EXAMPLE-02"],
  "cached_at":"2026-11-01T09:05:00Z"
}
```

`manifest_revision` is frozen after seal and is **not** identical to continuously incremented Shipment.version. To support this route, store `shipments.manifest_revision` updated during DRAFT manifest edits and fixed at seal.

`POST /courier/sync` schema and error handling are defined in [11-offline-sync-protocol.md](11-offline-sync-protocol.md), including a sample request and per-command results. Each entry carries a stable `client_command_id` (server idempotency key, stored under a single operation namespace `courier_offline_command` for all courier sync actions). Reusing the same ID for a different action or Shipment is a 409 per-command conflict. Server processes each command in its own transaction; a conflict does not roll back earlier successful commands in the batch.

**Offline-specific error codes:** `OFFLINE_COMMAND_STALE`, `MANIFEST_MISMATCH`, `IDEMPOTENCY_KEY_REUSED`, `INVALID_STATE`, `COURIER_ASSIGNMENT_REVOKED`. Individual command errors appear inside `results`; request-level 401 means none processed.

## 7. Auth / RBAC and audit deltas

- Introduce `LAB_MANAGER` in org membership: inherits Lab Operator operational permissions plus `reopen_receiving`, but not cross-organization writes.
- Introduce `REGIONAL_OPERATIONS` regional membership: resolves blocked deliveries and sees stalled metadata. It is **not** a global administrator and does not edit sample results.
- `ORG_ADMIN` retains scoped membership management, not operational override.
- `REGIONAL_ANALYST` remains aggregate-only.
- Use `request_id` and `actor_id` for all new events: `CONTAINER_ISSUE_REPORTED`, `DELIVERY_BLOCKED`, `DELIVERY_RETRY_AUTHORIZED`, `SHIPMENT_CLOSED_UNDELIVERED`, `RECEIVING_REOPENED`, `RECEIPT_CORRECTED`, `OFFLINE_COMMAND_APPLIED`.
- Explicitly avoid a second business state source in Redis or browser.

## 8. Consistent HTTP / error semantics

| Situation | HTTP |
|---|---|
| New container issue recorded | 201 |
| Conflict: repeated open issue for same container | 409 CONTAINER_ISSUE_ALREADY_OPEN |
| No matching manifest container / inaccessible Shipment | 404 masked where required |
| Wrong delivery status | 409 INVALID_STATE |
| Container reason code not active for kind/level | 422 INVALID_REASON_CODE |
| Unauthorized resolution | 403 or scoped 404 |
| Reopen from non-completed state | 409 INVALID_STATE |
| Unexpected concurrency race | 409 VERSION_CONFLICT |
| Offline partial result | 200 for valid authenticated batch with per-item error result |
| Offline authorization failure for entire request | 401/403 |
| Retry with identical idempotency key/payload | Return recorded authoritative response |

OpenAPI 3.1 can encode the union of receipt result requests with `oneOf`:
- ACCEPTED — result only, optional null reason_code/comment;
- MISSING or REJECTED — result + required reason_code, optional comment.

A syntactically valid reason code still requires semantic validation against active `issue_reason_codes` for the applicable scope and kind.

## 9. Change-management note

The earlier API draft is **not implemented**, so breaking changes to v0.4 are acceptable. Do not claim backwards compatibility with a deployed client that does not exist. Once actual clients are released, use API versioning and deprecation policy rather than silently changing contracts.
