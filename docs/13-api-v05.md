# LabTrack v0.5 — Изменения контракта API

> **Исторический документ (до v0.6).** Приоритет имеют [Решения v0.6](15-decisions-v06.md), [Доменная модель v0.6](16-domain-workflows-v06.md), [Модель данных v0.6](17-data-model-v06.md), [API v0.6](18-api-v06.md). Этот текст может содержать устаревшие правила передачи всей партии по принципу «всё или ничего» и одностороннего разрешения проблем; не использовать его как актуальный контракт.

**Базовый путь:** `/api/v1` · **Статус:** исторический контракт v0.5, спроектированный до реализации; на момент написания не был реализован и заменён контрактом API v0.6.1.
**Машиночитаемая версия:** [OpenAPI 3.1 JSON](../openapi/labtrack-v1.json) (черновик v0.5). Этот документ заменяет противоречащие ему правила исходного [REST API v0.4](09-api-specification.md).

## 1. Неизменные принципы

- Аутентификация с хэшами паролей Argon2id и короткоживущим Bearer JWT. Каждая операция проверяет текущего исполнителя и область доступа организации/региона; UUID и QR сами по себе не разрешают доступ.
- Один `Sample` на физическую пробирку внутри ровно одного `TransportContainer`; Shipment объединяет контейнеры. При запечатывании манифест становится неизменяемым.
- Передача требует **двух разных аутентифицированных людей**: отправитель и назначенный курьер, затем курьер и оператор лаборатории назначения. Подтверждённая передача контейнеров **не означает** приёмку пробирок.
- Результаты пробирок — `ACCEPTED`, `MISSING`, `REJECTED`; проблемы контейнеров — `MISSING` или `REJECTED`. Обе категории исключений требуют структурированных кодов причин.
- Команды записи атомарны с аудитом и идемпотентностью. Уведомления P0 остаются без гарантии доставки.

## 2. Изменённые и новые маршруты

| Метод | Маршрут | Разрешённая роль | Запрос | Успех / действие |
|---|---|---|---|---|
| `GET` | `/issue-reasons?scope=SAMPLE&kind=REJECTED` | Отправитель/курьер/лаборатория в своей области доступа | фильтр области/категории | 200, список активных кодов причин |
| `POST` | `/shipments/{id}/container-issues` | Назначенный курьер или оператор лаборатории назначения (REJECTED — только лаборатория) | `{container_id,kind,reason_code,comment?}` | 201; IN_TRANSIT/DELIVERY_PENDING → DELIVERY_BLOCKED |
| `GET` | `/shipments/{id}/container-issues` | Участник с доступом / REGIONAL_OPERATIONS региона | — | 200, список проблем |
| `POST` | `/shipments/{id}/container-issues/resolve` | REGIONAL_OPERATIONS того же региона | `{resolution,reason}` | 200; RETRY_DELIVERY → IN_TRANSIT или CLOSE_UNDELIVERED → CLOSED_UNDELIVERED |
| `POST` | `/shipments/{id}/receiving/reopen` | LAB_MANAGER лаборатории назначения | `{reason}` | 200; COMPLETED* → RECEIVING с новым сеансом приёмки |
| `GET` | `/shipments/{id}/receiving/history` | Лаборатория назначения или отправитель с доступом (только чтение) | постраничная выдача | 200, сеансы приёмки и версии результатов |
| `GET` | `/samples/{id}/external-references` | Исходный отправитель или лаборатория назначения после назначения | — | 200, непрозрачные ссылки в области доступа |
| `POST` | `/samples/{id}/external-references` | Исходный отправитель | `{system_code,reference_kind,external_id}` | 201, только синтетические непрозрачные ссылки |
| `GET` | `/courier/shipments/{id}/offline-manifest` | Назначенный курьер | — | 200, снимок манифеста для работы без сети после входа и проверки доступа (без данных пациентов) |
| `POST` | `/courier/sync` | Назначенный курьер с текущим активным членством | `{commands:[...]}` | 200, APPLIED/ALREADY_APPLIED/REJECTED/RETRYABLE по каждой команде |
| `GET` | `/operations/stalled-shipments` | REGIONAL_OPERATIONS | фильтр региона / возраста / статуса | 200, доступные запросом ожидающие/заблокированные случаи (без построчных данных пробирок) |

`/shipments/{id}/receiving/items/{item_id}` **меняет схему запроса**:

```json
{"result":"MISSING","reason_code":"SAMPLE_NOT_FOUND","comment":"QR не обнаружен при сверке"}
```

Для ACCEPTED поля `reason_code` и `comment` должны отсутствовать либо быть null. Для MISSING и REJECTED `reason_code` обязателен и должен быть активным для `scope=SAMPLE,kind=result`; комментарий необязателен, краевые пробелы удаляются, длина — не более 500 символов. Это заменяет старое свободное текстовое поле `reason` команд приёмки.

`Shipment.status` дополняется DELIVERY_BLOCKED и CLOSED_UNDELIVERED. Завершённый Shipment возвращается в RECEIVING только через команду повторного открытия руководителем лаборатории в своей области доступа; обычные пользователи не могут менять другие успешные конечные статусы.

## 3. Пример проблемы контейнера

Запрос:

```http
POST /api/v1/shipments/33333333-3333-4333-8333-333333333333/container-issues
Authorization: Bearer <token>
Idempotency-Key: 95959595-9595-4595-8595-959595959595
Content-Type: application/json

{
  "container_id":"44444444-4444-4444-8444-444444444444",
  "kind":"REJECTED",
  "reason_code":"CONTAINER_SEAL_UNACCEPTABLE",
  "comment":"Описание операционного отказа"
}
```

Ответ 201:

```json
{
  "issue": {
    "id":"55555555-5555-4555-8555-555555555555",
    "container_id":"44444444-4444-4444-8444-444444444444",
    "kind":"REJECTED",
    "status":"OPEN",
    "reason_code":"CONTAINER_SEAL_UNACCEPTABLE"
  },
  "shipment_id":"33333333-3333-4333-8333-333333333333",
  "shipment_status":"DELIVERY_BLOCKED"
}
```

Проблема контейнера `REJECTED` требует оператора или руководителя лаборатории назначения. Об отсутствии может сообщить курьер или оператор лаборатории назначения. Сервер проверяет наличие контейнера в запечатанном манифесте, даже если он физически не предъявлен.

В одной транзакции: создать проблему; отозвать ожидающую передачу доставки PENDING с причиной и `withdrawn_by`; перевести Shipment в DELIVERY_BLOCKED; добавить аудит. Все результаты пробирок остаются неизменными, приёмка запрещена.

**Без частичного успеха:** остальные контейнеры не считаются доставленными; вторая сторона не подтверждает заблокированную передачу.

## 4. Ручное разрешение

Запрос:

```json
{"resolution":"RETRY_DELIVERY","reason":"Контейнер найден и доступен для повторной передачи"}
```

Либо `{"resolution":"CLOSE_UNDELIVERED","reason":"Фактическая доставка не состоялась"}`.

- Только REGIONAL_OPERATIONS того же региона.
- Требуются Shipment в DELIVERY_BLOCKED, хотя бы одна соответствующая проблема и отсутствие противоречащего ожидающего сеанса приёмки.
- Разрешает/закрывает **все проблемы контейнеров OPEN** с исполнителем и причиной, атомарно меняя Shipment.
- RETRY_DELIVERY → IN_TRANSIT; следующая передача доставки — *новая попытка* с другим `attempt_no`.
- CLOSE_UNDELIVERED → CLOSED_UNDELIVERED, записывает `closed_at/closed_by/closure_reason`; никогда не считается доставкой или завершением.
- Автоматический переход физического владения или правовой ответственности не подразумевается. Правила фактического обращения с отклонёнными контейнерами нужны до реального пилота.

## 5. Повторное открытие и история приёмки

Запрос:

```http
POST /api/v1/shipments/33333333-3333-4333-8333-333333333333/receiving/reopen
Authorization: Bearer <token>
Idempotency-Key: ccccccdd-cccc-4ccc-8ccc-cccccccccccc
Content-Type: application/json

{"reason":"При проверке выявлена ошибочная отметка пробирки"}
```

- Только LAB_MANAGER лаборатории назначения, для COMPLETED/COMPLETED_WITH_ISSUES и лишь при существующем предыдущем сеансе CLOSED.
- В одной транзакции: заблокировать Shipment, создать следующий сеанс OPEN, перевести статус в RECEIVING, добавить аудит, увеличить версию.
- Последнее существующее `container_items.receipt_result` не меняется; редактирование в сеансе добавляет `receipt_revisions`. Сброса в null нет.
- Закрытие заново проверяет все позиции и выводит COMPLETED / COMPLETED_WITH_ISSUES. Старые сеансы и аудит остаются видимыми в истории.
- Только один сеанс OPEN; конкурентные попытки повторного открытия сериализуются, одна получает 409, кроме повторов с тем же ключом идемпотентности.

История приёмки упорядочена хронологически и ограничена областью доступа. Предоставлять `changed_by` и `changed_at`, но никогда учётные данные, исходные записи пациентов или ненужные данные безопасности.

## 6. Контракт работы курьера без сети

**Ответ с манифестом для работы без сети:**

```json
{
  "shipment_id":"33333333-3333-4333-8333-333333333333",
  "manifest_revision":4,
  "status":"PICKUP_PENDING",
  "container_codes":["LT-C-EXAMPLE-01","LT-C-EXAMPLE-02"],
  "cached_at":"2026-11-01T09:05:00Z"
}
```

`manifest_revision` фиксируется после запечатывания и **не совпадает** с постоянно растущим Shipment.version. Для маршрута хранить `shipments.manifest_revision`, обновляя при изменениях манифеста в DRAFT и фиксируя при запечатывании.

Схема `POST /courier/sync` и обработка ошибок определены в [11-offline-sync-protocol.md](11-offline-sync-protocol.md), включая пример запроса и результаты отдельных команд. Каждая запись содержит стабильный `client_command_id` (серверный ключ идемпотентности в едином пространстве операций `courier_offline_command` для всех действий синхронизации курьера). Тот же ID для другого действия или Shipment даёт конфликт 409 отдельной команды. Сервер обрабатывает каждую команду в собственной транзакции; конфликт не откатывает предыдущие успешные команды пакета.

**Коды ошибок режима без сети:** `OFFLINE_COMMAND_STALE`, `MANIFEST_MISMATCH`, `IDEMPOTENCY_KEY_REUSED`, `INVALID_STATE`, `COURIER_ASSIGNMENT_REVOKED`. Ошибки отдельных команд — внутри `results`; 401 уровня запроса означает, что ничего не обработано.

## 7. Изменения аутентификации, RBAC и аудита

- Ввести `LAB_MANAGER` в членстве организации: наследует операционные права оператора лаборатории и `reopen_receiving`, без записи в других организациях.
- Ввести региональное членство `REGIONAL_OPERATIONS`: разрешает блокировки и видит метаданные зависших партий. Это **не** глобальный администратор; результаты пробирок он не редактирует.
- `ORG_ADMIN` сохраняет управление членством в своей области доступа, без обхода операционных правил.
- `REGIONAL_ANALYST` по-прежнему видит только агрегаты.
- Использовать `request_id` и `actor_id` во всех новых событиях: `CONTAINER_ISSUE_REPORTED`, `DELIVERY_BLOCKED`, `DELIVERY_RETRY_AUTHORIZED`, `SHIPMENT_CLOSED_UNDELIVERED`, `RECEIVING_REOPENED`, `RECEIPT_CORRECTED`, `OFFLINE_COMMAND_APPLIED`.
- Явно исключить второй источник бизнес-состояния в Redis или браузере.

## 8. Единая семантика HTTP и ошибок

| Ситуация | HTTP |
|---|---|
| Новая проблема контейнера записана | 201 |
| Конфликт: повторная открытая проблема того же контейнера | 409 CONTAINER_ISSUE_ALREADY_OPEN |
| Нет контейнера в манифесте / Shipment недоступен | 404, со скрытием существования при необходимости |
| Неверный статус доставки | 409 INVALID_STATE |
| Код причины контейнера неактивен для категории/уровня | 422 INVALID_REASON_CODE |
| Нет полномочий на разрешение | 403 либо 404 с учётом области доступа |
| Повторное открытие из незавершённого состояния | 409 INVALID_STATE |
| Неожиданная гонка конкурентного доступа | 409 VERSION_CONFLICT |
| Частичный результат действий без сети | 200 для допустимого аутентифицированного пакета с ошибками по позициям |
| Ошибка авторизации всего запроса без сети | 401/403 |
| Повтор с тем же ключом идемпотентности и данными | Вернуть сохранённый достоверный ответ |

OpenAPI 3.1 может описать объединение запросов результатов приёмки через `oneOf`:
- ACCEPTED — только результат, необязательные null reason_code/comment;
- MISSING или REJECTED — результат и обязательный reason_code, необязательный comment.

Синтаксически допустимый код причины всё равно требует смысловой проверки по активным `issue_reason_codes` для соответствующей области и категории.

## 9. Примечание об управлении изменениями

На момент написания этот ранний проект API **не был реализован**, поэтому несовместимые изменения v0.4 были допустимы. Не заявлять обратную совместимость с развёрнутым клиентом, которого тогда не было. После выпуска реальных клиентов использовать версионирование API и политику вывода из эксплуатации вместо незаметного изменения контрактов.
