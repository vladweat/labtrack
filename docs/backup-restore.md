# Проверка резервного копирования и восстановления синтетической песочницы

## Что покрывает проверка

Корневой `compose.yaml` поднимает PostgreSQL 15 с портом только на интерфейсе обратной петли и именованным томом. Миграции выполняются ролью-владельцем БД; приложение использует отдельную роль с правами DML. API запускается отдельно от этого файла Compose. Проект `labtrack-demo-sandbox` и том `labtrack_demo_sandbox_postgres_data` отделены от среды разработки и публичного демонстрационного стенда.

В репозитории не было воспроизводимой проверки восстановления с проверкой версии Alembic, данных рабочего процесса и прав роли приложения. Контрольная проверка публичного демонстрационного стенда — это неаутентифицированные GET-проверки интерфейса и готовности, а не проверка восстановления. Рабочая копия развёртывания и её базовая конфигурация Compose не входят в эту проверку; она не доказывает восстановимость публичного демонстрационного стенда или производственной среды.

Скрипт выполняет `pg_dump` в специальном формате только из локальной БД `labtrack_demo_sandbox`, для которой явно разрешена проверка. PostgreSQL формирует архив из согласованного снимка одной БД. До и после выгрузки скрипт сравнивает версию схемы, выбранные количества записей и синтетические инварианты; при изменении данных проверка завершается ошибкой. Заранее остановите API и процессы записи, чтобы сравнение было стабильным.

Архив восстанавливается в новую БД с именем `labtrack_restore_test_<12 hex>`. Перед созданием проверяется отсутствие БД; после создания проверяются имя, владелец, `datistemplate=false` и разрешение подключения. Произвольные имена, включая `postgres`, `labtrack` и имена производственных БД, отклоняются. Проверяющий PostgreSQL запускается с `--network none` и хранит каталог данных в tmpfs. Тестовая БД удаляется после проверки, а контейнер удаляется при успехе и обычной ошибке.

Проверка сравнивает последнюю версию миграций Alembic и количества записей таблиц `regions`, `organizations`, `users`, `samples`, `shipments`, `transport_containers`, `container_items`, `handoffs` и `audit_events`. Она также требует синтетический адрес электронной почты с доменом `.example.test`, организацию `DEMO_SENDER` и хотя бы одну связь `Shipment` → `TransportContainer`. Роль приложения восстанавливается тем же скриптом инициализации, затем проверяются права входа, подключения, чтения и записи, отсутствие прав владельца или администратора, `CREATE` на базу данных и схему, `TRUNCATE` и `TRIGGER`. Финальный запрос рабочего процесса выполняется от этой роли в транзакции `READ ONLY`. Перед ним проверяется парольная аутентификация роли.

## Запуск локально

Сначала создайте изолированную синтетическую демонстрационную БД, примените миграции и выполните `seed-demo` по шагам [руководства развёртывания демонстрационного стенда](deploy.md). Используйте только локальный `.env.demo.sandbox` с правами `0600`. Убедитесь, что в этом проекте Compose запущен только PostgreSQL; остановите локальный API и все процессы, которые могут писать в БД. Скрипт дополнительно откажется работать при других запущенных сервисах Compose или активных сеансах БД роли приложения.

Нужны Docker Compose, серверное окружение `.venv` с зависимостями разработки и уже кешированный образ `postgres:15`. Скрипт не скачивает образы. Из корня репозитория:

```bash
docker image inspect postgres:15 >/dev/null
docker compose --project-name labtrack-demo-sandbox \
  --env-file .env.demo.sandbox --file compose.yaml ps
install -d -m 700 backups
archive="backups/labtrack-demo-$(date -u +%Y%m%dT%H%M%SZ).dump"
cd backend
.venv/bin/python -m app.ops.backup_restore_drill --archive "../$archive"
cd ..
(cd backups && sha256sum -c "$(basename "$archive").sha256")
```

Команда читает закрытый файл окружения сама, не исполняет его как командный сценарий и не печатает значения. Для проверки отказа по имени можно передать, например, `--restore-database labtrack`; цель будет отклонена до обращения к Docker. Используйте новый путь для каждого архива: существующие архив или контрольная сумма никогда не перезаписываются.

При успешной проверке команда оставляет `.dump` и `.sha256` в `backups/`, оба файла имеют права `0600`. Временная восстановленная БД и контейнер удаляются. При ошибке неполные архив и контрольная сумма удаляются, а исходная БД не изменяется. Сообщения команды не включают пароли, адреса электронной почты или содержимое строк; подробный вывод дочерних процессов намеренно подавляется. Пароли поступают из `.env.demo.sandbox` и не передаются в аргументах команд. Пользователи службы Docker всё равно могут просматривать окружение работающих контейнеров.

## Хранение и ограничения

- Восстановление проверено только для согласованного снимка одной БД PostgreSQL. Архивирование WAL, восстановление на момент времени, восстановление ролей кластера, состояния Redis/Celery и согласование с внешними системами не реализованы.
- Автоматической ротации и заданного срока хранения нет. Оператор выбирает срок хранения, ограничивает доступ, удаляет устаревшие файлы и при переносе использует утверждённое шифрование. Не добавляйте архивы или файлы окружения в Git, артефакты CI, задачи или публичные журналы.
- Архив содержит синтетические учётные записи, хеши паролей, данные аудита и рабочего процесса; несмотря на синтетический характер данных, храните его как закрытый файл.
- Эта процедура проверяет восстановление из `pg_dump`, но не резервное копирование тома, не аварийный узел восстановления и не SLA. Не используйте её для БД публичного демонстрационного стенда или производственной среды.
- `.github/workflows/public-demo-smoke.yml` по-прежнему выполняет только GET-запросы без аутентификации. Любую будущую сквозную контрольную проверку с аутентификацией запускайте только на отдельной контролируемой БД тестового стенда или тестовых данных с собственными синтетическими учётными записями, томом и процедурой сброса; не входите и не меняйте данные общего публичного демонстрационного стенда.

CI запускает модульные проверки безопасности в процессе CI серверной части с отдельным сервисом `labtrack_test`. Они используют адаптер восстановления в памяти, не вызывают Docker и не имеют адреса узла или конфигурации производственной среды. Реальная проверка восстановления запускается только вручную в локальной песочнице.
